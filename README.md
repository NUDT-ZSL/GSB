团队拿到的验收清单上只有一小段关于 SQL 解析与逻辑计划的文字说明，工作区目前还没有任何可运行代码或样本。本项目要在 Linux（WSL Ubuntu）本地交付一个独立的数据处理管线与结果验证工具，围绕 SQL 逻辑计划在两代格式快照与补丁编辑下的互操作性和依赖失效问题展开。全部输入由随题交付的固定种子脚本确定性生成，不依赖真实数据库、外部服务或网络。业务对象包括：v1 单文件 JSON 快照（视图名、SQL 文本、扁平列映射、相对生成秒数），v2 分片 JSON 加 SQLite 元数据库（视图规范名、计划代数、绝对生成毫秒、列级依赖摘要与失效墓碑），以及按逻辑时钟注入的视图编辑补丁流，支持对 SQL 文本与依赖上游做新增、修改、删除。管线需解析 SQL 生成逻辑计划树，跨版本合并快照与时间语义，在补丁驱动下沿依赖图计算精确失效闭包，判定哪些计划与可执行 SQL 需重算，并支持中断恢复与多进程并发一致性。

任务环境与准备：
在 Linux（WSL Ubuntu）环境准备 Python 3.10 或更高版本。
安装依赖：pip install sqlparse（SQLite 使用 Python 标准库 sqlite3）。
使用随题交付的固定种子脚本生成样本目录，包含 v1_snapshot.json、v2_shards/ 与 sqlite_meta.db、view_definitions.json、patch_events.jsonl。
确保 SQLite 数据库文件位于工作区可写目录，样本生成脚本无需联网。

业务要求：
1. 实现视图定义集合与两代逻辑计划快照的解析校验：视图名唯一且非空，SQL 文本可被 sqlparse 解析为合法结构，依赖上游视图存在且在定义集合中，依赖图无自环，逻辑时钟毫秒为非负整数，v1 扁平列映射条目均可追溯到已声明的视图与列且相对生成秒数为非负整数，v2 分片文件哈希与计划代数单调递增，任何非法输入映射到不同业务错误码并保留可诊断字段。
2. 实现 SQL 文本到逻辑计划树的确定性转换：使用 sqlparse 把每个视图的查询解析为包含扫描、过滤、投影、聚合与联接节点的计划树，抽取每个节点的输出列、谓词引用列与联接键，同一 SQL 在任意运行次数下必须得到逐字一致的计划树与节点摘要，作为跨版本合并与失效闭包计算的稳定标识。
3. 实现跨版本快照合并与统一计划视图构建：同一视图在两代快照中同时存在时，依据快照声明的逻辑时钟与计划代数裁决最新计划，逻辑时钟相同则按来源格式优先级裁决，合并后每个视图须保留来源版本、原始时间表示与裁决依据，v1 相对生成秒数在注入逻辑时钟下换算为绝对毫秒并记录换算标度与舍入方向。
4. 实现编辑补丁驱动的依赖失效闭包裁决：以补丁提交视图新增、修改与删除，沿“视图—上游视图—列引用—已缓存计划—下游可执行 SQL”的依赖关系计算受影响闭包，精确标记哪些计划与下游视图需重算、哪些可安全复用，未受影响视图的已缓存计划与可执行 SQL 必须逐字节不变，失效来源以补丁序号与依赖路径形式可追溯。
5. 实现列级依赖的细化失效与命名变化裁决：视图中投影列名变化、别名变化或删除被下游引用的列时，失效必须细化到引用该列的节点与视图而非整条查询树，下游视图在解析期即可判定为不可编译时须返回独立业务错误码并输出首个缺失列与引用路径，保证失效闭包不扩大也不遗漏。
6. 实现编辑轮次的增量推进与整体替换及强制终止后的恢复：把当前计划快照指针、各视图计划摘要、失效事件与逻辑时钟水位以事务原子写入 SQLite，每次编辑产生新计划快照代数并以临时表加代数整体替换指针而非逐条覆盖，进程在解析、失效计算或快照替换中途被强制终止后，恢复路径依据持久化状态识别已提交编辑与半提交计划，只重放未完成部分且不得重复计入失效事件或使视图计划出现新旧混合。
7. 实现多进程并发一致性与幂等提交：允许多个编辑处理进程与快照更新进程并行操作同一批视图，通过 SQLite 事务与文件锁保证同一视图同一编辑轮次只被提交一次、同一计划快照代数只被整体替换一次，重复提交相同补丁必须幂等，读取方在任意时刻只能看到完整已提交的计划快照且不得观察到部分更新的列映射或计划树。
8. 实现异常链路隔离与可重复命令行验证：SQL 语法错误、依赖成环、引用不存在的列、分片哈希不匹配、计划代数回退、逻辑时钟回拨超过容差分别映射到不同业务错误码并在输出中保留可诊断字段（视图名、节点标识、编辑轮次），单个视图编辑失败不得中断其他视图的已提交状态，提供 load、parse、merge、patch、resume、status、verify 子命令并以稳定排序 JSON 输出结果。
