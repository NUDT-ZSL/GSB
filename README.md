当前是空白工作区，需要从零实现一个本地多租户压测批次容量评估与诊断工作台。本地场景由 JSON 给出：目标服务清单（服务名、回环监听端口、每个租户的 SLO 成功率下限与 P95 延迟上限）、压测批次计划（批次号、租户、并发梯度序列、每梯度持续逻辑毫秒、每梯度请求节奏、是否允许提前终止）、逻辑时钟步进表。目标服务由本地可编程 HTTP 测试服务模拟，可按租户路径返回可配置的状态码分布、慢响应与连接拒绝，并支持人为在指定逻辑窗口返回故障。工作台需把批次拆分成“租户—并发梯度—观测窗口”三层单元，在每租户并发预算与全局逻辑时间预算约束下并行驱动压测单元，采集观测窗口摘要并裁决每个梯度是否达到容量拐点，据此给出每租户的容量结论。核心难点在于：租户并发梯度之间会争抢全局预算，梯度提前终止会改变后续梯度的基线；中断后必须依据持久化水位只补测未完成窗口，并让续测结果与未中断结果逐位一致。同时要提供可视化诊断输出，解释每个容量结论依赖哪些观测窗口与异常分类计数。

任务环境与准备：
安装 Python 3.11 或以上版本，并确保 pip 可用；在 Windows 命令行中创建虚拟环境并激活。
安装依赖：pip install numpy pytest httpx；不安装 Docker 或任何容器运行时。
准备本地样本：一个 JSON 场景文件（目标服务清单、压测批次计划、逻辑时钟步进表）、一个本地 HTTP 测试服务脚本（使用 Python http.server 或 Flask，监听 127.0.0.1 的可分配端口，按租户路径返回可配置状态码、慢响应与连接拒绝，并支持在指定逻辑窗口返回故障）。
运行前先在 Windows 上启动本地 HTTP 测试服务，并确认其监听回环地址与场景文件中的端口一致。
为持久化状态准备本地 SQLite 数据库文件路径；演示脚本按固定随机种子与固定场景重复运行两次，并保存每次生成的报告用于比对。

业务要求：
1. 实现目标服务清单、压测批次计划与逻辑时钟步进表的解析校验：服务名与租户名唯一、监听地址为合法回环地址、并发梯度序列严格递增且元素为正整数、持续逻辑毫秒与请求节奏参数合法、SLO 阈值区间有效；非法输入必须返回明确业务错误码（如 E_BAD_PLAN）且不写入任何持久化状态。
2. 实现基于可注入逻辑时钟的压测单元驱动：批次被切分为“租户—并发梯度—观测窗口”三层单元，请求节奏、持续时长与窗口归属只依据注入的逻辑时钟毫秒值推进，不得读取系统墙钟；同一计划与同一服务响应序列在任意运行次数下必须得到逐位一致的请求序列、窗口归属与窗口摘要。
3. 实现每租户并发预算与全局逻辑时间预算双重约束下的并行单元调度：同一轮次内按租户分组并行驱动压测单元，同时受每租户并发梯度上限与全局逻辑时间预算约束；预算耗尽必须放弃剩余未启动单元并记录放弃原因，且必须区分预算内未启动、启动后失败与主动提前终止三类结局，已启动单元不得被简单截断为超时。
4. 实现观测窗口摘要与错误分类：按窗口统计请求数、成功数、以及按状态码不符、连接拒绝、响应超出单请求逻辑预算、畸形响应、目标服务中断分类的错误计数，并以固定排序与插值规则计算 P95 延迟；每类异常须保留可诊断字段（租户、梯度序号、窗口号、请求序号区间），单个异常不得污染其他窗口摘要。
5. 实现容量拐点判定与提前终止语义：依据每梯度窗口摘要与租户 SLO 阈值裁决梯度通过、降级通过或中止，并据此决定是否推进到下一梯度；提前终止必须记录触发的窗口号与阈值证据，且终止后不得把未执行梯度计为失败；已中止租户的容量结论必须与后续梯度解耦，不得因后续梯度继续执行而改变。
6. 实现强制终止后的恢复一致性：把每单元已提交窗口水位、窗口摘要、梯度结论、请求序列号水位与逻辑时钟水位以事务原子写入 SQLite；进程在任意单元被强制终止后，恢复路径依据持久化状态识别已提交窗口与半提交窗口，只补测未完成窗口并继续推进，恢复后各租户容量结论与未中断运行逐字段一致。
7. 实现多进程并发一致性与幂等提交：允许多个评估实例并行驱动不同租户或同一租户的不同梯度，通过 SQLite 事务与文件锁保证同一单元同一窗口同一版本只提交一次、全局逻辑时间预算不被并发超用，重复提交相同窗口结果必须幂等；读取方只能看到完整已提交的阶段结论而非中间态。
8. 提供命令行接口与诊断可视化输出：支持 run、resume、status、report、verify 子命令；report 以稳定排序 JSON 输出每个租户的容量结论、各梯度窗口摘要、容量拐点证据链与异常分类计数，status 输出各单元进度与逻辑时钟当前位置；verify 校验持久化状态与报告的一致性，并提供可重复演示脚本。
