当前是空白工作区，需要从零构建一个面向本地 Windows 环境的消息投递语义中间件，聚焦不同格式版本之间的互操作与兼容。系统在回环 TCP 端口上以 JSON 行协议接收生产者投递的消息，消息按至少三种格式版本编码：v1 只含消息体与投递标识，v2 增加整数毫秒级时间戳与至少一次投递所需的重试计数，v3 增加分区键与幂等序列号。消费者以不同版本声明订阅并接收消息，中间件须把高版本消息按低版本订阅者能力降级、把低版本消息按高版本语义补齐，并保证投递语义（至多一次、至少一次、恰好一次的可判定条件）在版本互操作中不被破坏。中间件以本地文件持久化投递日志、偏移量与去重索引，进程被强制终止后须依据持久化状态恢复；同时提供数据处理管线与结果验证工具，用于校验一次投递会话的格式转换、语义判定与结果是否符合预期。

任务环境与准备：
安装 Go 1.21 或以上与带 Tkinter 的 Python 3.10 或以上，确认 go 与 python 命令可用。
准备本地样本消息文件、生产者与消费者脚本目录，以及用于存放投递日志的临时目录，执行前清空。
无需网络、外部账号或容器环境，所有通信限定在回环端口，演示脚本按固定顺序调用本地命令。

业务要求：
1. 实现 JSON 行协议的消息接收与三版本编解码：解析生产者投递消息，校验必需字段、类型与格式版本号，v1 缺时间戳、重试计数、分区键与幂等序列号，v2 增加整数毫秒时间戳与非负重试计数，v3 再增加分区键与幂等序列号；未知版本须返回 E_VERSION 并拒绝该消息，失败不得影响同连接后续消息。
2. 实现消费者订阅声明与跨版本降级、补齐转换：消费者以声明版本订阅并接收消息，向低版本订阅者投递时须按明确规则剥离其不支持的字段并记录被剥离的字段集合，向高版本订阅者投递低版本消息时须补齐默认字段并标注为补齐而非原始提供；转换结果须可回溯到源消息标识与源格式版本。
3. 实现三种投递语义的可判定实现：至多一次不得重投，至少一次须在未确认时重投且重试计数递增，恰好一次须以幂等序列号去重使同一投递标识与序列号的重复投递只产生一次可消费结果；语义判定须在版本降级补齐后仍成立，幂等键缺失时须以 E_SEMANTIC 拒绝恰好一次投递。
4. 实现投递日志、偏移量与去重索引的本地持久化：消息体、投递标识、格式版本、消费者偏移与去重索引以本地文件追加持久化，偏移量须单调递增且与消费者确认对应；去重索引在恰好一次语义下跨重启保持有效，重复序列号须稳定返回既有结果而不重复落盘。
5. 实现并发投递下的顺序与去重一致性：多个生产者连接与多个消费者并发投递时，同一分区键内的投递顺序须与日志写入顺序一致，跨分区键不得出现半写记录；恰好一次语义下同一幂等序列号被并发重复投递时必须收敛为唯一结果，不得两边都写入成功。
6. 实现强制终止后的恢复与状态校验：进程被强制终止后重启须依据持久化日志与偏移量恢复消费者位置与去重索引，恢复报告须列出已恢复偏移、重建的去重索引条目数与尾部不完整记录的处理方式；恢复后未确认消息的重投行为须符合其投递语义，且不得重复已确认消息。
7. 实现格式互操作结果验证工具：读取投递日志与转换记录，逐条校验每条投递的源版本、声明版本、实际字段集合与语义判定是否自洽，降级剥离与补齐默认字段须与订阅者版本一致，校验失败须以 E_VERIFY 报告并列出偏差的投递标识、字段与期望值。
8. 提供交互界面与可重复演示管线：以 Tkinter 界面展示消息流、格式版本、转换方向、被剥离或补齐的字段、消费者偏移与语义判定，渲染顺序稳定；附带本地确定性样本生产者与消费者脚本及演示脚本，顺序执行三版本混合投递、某一订阅者重启后续投递与强制终止恢复三个场景，输出稳定顺序的验证总结。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
使用本地样本完成三版本混合投递、语义校验、故障恢复与验证工具总结，确认格式转换与投递语义一致。
