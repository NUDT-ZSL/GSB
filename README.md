在全新工作区中，需要从零实现一个平台故障恢复配置的增量补丁与依赖失效裁决引擎，用于在确定性样本上复现多代恢复配置在故障切换与回切过程中以补丁增量更新后的依赖失效闭包计算、恢复计划重建与中断恢复一致性。本地样本以 JSON 给出两代恢复配置：v1 为单文件 JSON，记录服务名、故障域、恢复动作脚本（按逻辑时钟描述启停与切换步骤）、相对回退秒数与扁平服务到动作映射；v2 为分片 JSON 加 SQLite 元数据库，记录服务规范名、绝对生效时刻毫秒戳、恢复代数、动作优先级标签、依赖上游服务列表与失效墓碑。引擎需加载并合并两代配置为统一恢复计划，接受补丁形式的新增、修改、删除与墓碑标记，沿依赖边精确计算受影响闭包，使未受影响的切换与回切结论可安全复用，并在进程被强制终止后依据持久化状态恢复裁决。

任务环境与准备：
安装 Python 3.11 及以上版本，确保 python 与 pip 可在 Windows 命令行直接调用。
执行 pip install pytest 安装测试依赖；SQLite 使用 Python 标准库 sqlite3，无需额外安装。
在工作区创建本地样本目录，按题面字段准备 v1 单文件 JSON、v2 分片 JSON 与元数据样例及注入逻辑时钟步进表；不得依赖网络、真实账号或外部站点。

业务要求：
1. 实现 v1 与 v2 两代恢复配置的解析与校验：v1 校验服务名唯一、相对回退秒数为非负整数、动作脚本步骤在注入逻辑时钟上非降序、扁平映射与动作声明一致；v2 校验分片文件哈希、SQLite 元数据中恢复代数单调、绝对生效时刻为整数、依赖上游服务存在且依赖图无自环；非法输入须返回明确业务错误码（如 E_BAD_CONFIG、E_CYCLE、E_HASH_MISMATCH），且不得写入任何持久化状态。
2. 实现跨版本合并与统一恢复计划构建：同一服务在两代配置中同时存在时，依据配置声明的逻辑时钟与恢复代数裁决最新版本，逻辑时钟相同则按来源格式优先级；合并后每条动作须保留来源版本、原始时间表示与原始相对回退值，并以稳定排序 JSON 输出裁决依据，使相同输入在任意运行次数下得到逐位一致的合并结果。
3. 实现时间表示的语义迁移：v1 的相对回退秒数在注入逻辑时钟下换算为绝对回退时刻并记录换算标度与舍入方向，v2 绝对时刻保持原值；迁移决策须持久化，同一逻辑时钟下重复判定逐位一致，并在计划中显式标记迁移后时间来源，使回切窗口比较不被重复换算。
4. 实现切换与回切的裁决执行链：按依赖拓扑序逐服务裁决切换动作是否可执行，上游未就绪时下游必须等待并记录触发来源；回切按配置的流量比例阶梯推进，每一步须校验目标服务健康结论与持久化状态，中途失败停留在上一稳定阶梯并输出失败证据，不得跳过阶梯或回退到未验证状态。
5. 实现补丁驱动的依赖失效闭包与结论复用裁决：以补丁形式提交服务依赖上游、动作步骤、流量阶梯或墓碑标记的修改，沿“服务—依赖上游—恢复动作—计划执行结论”的关系计算受影响闭包，精确标记哪些切换与回切结论需重算、哪些可安全复用；未受影响服务的结论、来源版本与证据链必须逐字保持不变。
6. 实现逻辑时钟注入与精度一致判定：所有生效判定、动作窗口与回退时刻换算只依赖注入的逻辑时钟毫秒值，不得读取系统墙钟；同一逻辑时钟序列下重放必须得到逐位一致的裁决序列，逻辑时钟回拨超过容差时返回业务错误码 E_CLOCK_REGRESS 并保持状态不变，而非静默接受。
7. 实现强制终止后的恢复裁决与配置包整体替换识别：把服务阶段、已提交动作水位、流量阶梯、迁移决策与逻辑时钟水位以事务原子写入 SQLite；进程在切换或回切任一阶段被强制终止后，恢复路径依据持久化状态识别已提交动作与半提交动作，只重放水位之后的动作；收到新配置包时比较清单版本号、恢复代数下限与分片哈希，判定完整替换、增量追加或无需操作，整体替换须以临时表加版本号切换计划指针而非逐条覆盖，版本回退须被拒绝。
8. 实现多进程并发一致性、幂等与异常链路隔离：允许多个编排实例并行处理同一批服务，通过 SQLite 事务与文件锁保证同一服务同一动作版本只被提交一次、重复提交幂等、读取方只看到完整已提交阶段；动作目标连接拒绝、动作超出单次逻辑预算、分片哈希不匹配、依赖成环、配置代数冲突、逻辑时钟回拨分别映射到不同业务错误码并保留可诊断字段，单个服务异常不得中断其他服务的裁决。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
