当前是空白工作区，需要从零构建一个面向本地 Windows 环境的顺序消息中间件组件，聚焦分区内严格有序投递、失败重投与消费位点账本的跨版本状态一致性。系统在本地回环 TCP 上以 JSON 行协议接收生产者追加消息，消息带分区键、生产者序列号与服务端分配的单调追加位点；同一分区键内消息必须按追加位点顺序被消费。消费端以拉取方式获取某一分区的下一批消息，并提交消费位点；服务端须维护每个分区已提交位点、投递中窗口与重投计数。当消费端处理失败或多个消费端同时拉取同一分区时，服务端须保证分区内的重投仍然保持原有顺序，不出现后序消息越过被重投的前序消息被确认；同时把投递日志与位点账本持久化到本地 SQLite，进程中断后依据持久化状态恢复分区有序性与重投语义。另需一个可复现验证工具，用本地确定性样本与故障注入脚本判断顺序消息语义是否被破坏。

任务环境与准备：
安装 Go 1.21 或更高版本并确认 go 命令在 PATH 中可用，启用本地模块缓存，不引入任何外部网络依赖。
确认本地 SQLite 驱动可离线编译（使用纯 Go 的本地驱动并以 go mod vendor 或本地模块缓存方式提供），无需容器或数据库服务端。
准备本地确定性样本：生产者消息序列 JSONL、消费者处理结果标记脚本与故障注入参数文件，全部位于工作区 data 目录下。
确认可使用回环 TCP 高位端口与 Windows 子进程，运行演示脚本前检查端口未被占用。
预留工作区 output 目录用于存放 SQLite 数据库、恢复报告、结构化日志与验证工具报告。

业务要求：
1. 实现消息追加与分区键路由：生产者以 JSON 行协议提交消息，服务端校验分区键合法、生产者序列号在同一生产者会话内单调递增、消息体长度在边界内，任一不合法须以 E_APPEND 业务码拒绝且不消耗追加位点；同一分区键的消息须被分配严格递增且连续的追加位点，分配结果须写入持久化日志后才向生产者回执，回执中位点必须与实际持久化位点一致。
2. 实现拉取与投递窗口管理：消费端按分区声明拉取批次上限，服务端只向每个分区当前唯一活跃的消费会话发放该分区下一个未确认位点开始的消息窗口；同一分区已有未过期投递窗口时新的拉取须被拒绝并返回 E_FENCE 并给出持有窗口的会话标识，窗口在提交确认或超时后释放，窗口超时的判定须以服务端单调时钟为准并记录超时事件。
3. 实现有序重投语义：当消费端对窗口内某条消息报告失败或窗口超时，服务端须从该窗口最早未确认位点起整体重新投递，不得跳过该位点而投递后续消息；重投次数须逐位点记录并在超过上限时以 E_POISON 将该分区标记为阻塞且输出阻塞位点与重投计数，阻塞分区在人工确认清理前不得继续发放后续消息，失败注入只改变输入消息的处理结果标记。
4. 实现位点账本与消费提交校验：消费端提交的位点须属于当前投递窗口内且不得跳跃，跳跃或回退提交须以 E_COMMIT 拒绝并保留原已提交位点不变；账本须持久化每个分区的已提交位点、窗口边界与重投计数，提交成功后窗口随之收紧，且任意时刻已提交位点必须小于等于已确认位点，账本与投递窗口的对应关系须可被查询命令逐分区导出。
5. 实现并发拉取与提交的分区隔离：多个消费会话并发操作不同分区时须互不干扰，同一分区的并发拉取与提交由分区级互斥保证结果唯一确定；并发提交与窗口超时同时发生时结果必须唯一，不允许既提交成功又被记为超时重投，隔离结果须在结构化日志中体现先发生的事件及其依据。
6. 实现强制终止后的恢复与恢复报告：进程被强制终止后重启须依据 SQLite 中持久化的日志与账本恢复各分区已追加位点、已提交位点与重投计数，恢复报告须列出恢复的分区数、重投未决位点与尾部不完整记录的处理方式；未确认窗口须在下一次拉取时按有序重投重新发放，恢复过程不得承诺产生退出报告，也不得以内存顺延掩盖持久化缺口。
7. 实现格式与状态版本识别及整体替换：消息日志与位点账本须带整数格式版本号，格式版本或分区账本版本变化时须识别差异并以整体替换方式重建内存分区状态，禁止把新旧账本字段增量合并；恢复或升级后须对每个分区重新校验已提交位点、窗口边界与重投计数之间的约束，校验失败以 E_LEDGER 报告该分区不一致的具体字段。
8. 实现可复现验证工具与异常注入：验证工具读取持久化日志与账本，按分区独立重放追加序列与提交序列，校验最终消费顺序、已提交位点与重投计数是否与账本一致，不一致以 E_VERIFY 列出首个违背顺序的分区与位点；支持以命令行参数注入分区键非法、位点账本损坏、消费失败持续超过重投上限三类异常，分别以 E_APPEND、E_LEDGER、E_POISON 报告并写入结构化日志，附带确定性样本生产者与消费者脚本及顺序执行正常投递、失败重投、强制终止后恢复三种场景的演示脚本。
