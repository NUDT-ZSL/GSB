在空白工作区从零实现一个本地消息投递网关的投递语义管理层，核心是让两代消息信封格式在同一个投递管线中互操作，并保持至少一次投递、去重与死信判定语义一致。本地样本提供三段消息存档：v1 信封为单文件 JSON 行，记录消息 ID、主题、正文、投递计数与相对过期秒数；v2 信封为分片 JSON 加 SQLite 元数据库，记录消息 ID 规范形式、分区键、绝对过期毫秒时间戳、投递代数、重试标签与死信墓碑。网关需加载并合并两代存档，构建统一投递队列，在可注入逻辑时钟下执行消费确认、重投、过期与死信迁移，并识别存档整体替换时的版本变化。消费方由本地确定性模拟器扮演：按消息 ID 返回确认、拒绝或丢弃结果，可注入重复投递与迟到确认。全部状态持久化到 SQLite，进程被强制终止后需依据持久化状态恢复。

任务环境与准备：
Windows 本地安装 Python 3.11 或以上，确认 sqlite3 模块可用；无需容器、外部服务或网络访问。
在空白工作区准备本地样本：v1 单文件 JSON 行存档与 v2 分片 JSON 加 SQLite 元数据库各一份，含逻辑时钟声明、投递代数、墓碑标记与少量畸形条目用于异常验证。
准备确定性消费方模拟器样本脚本，按消息 ID 返回确认、拒绝或丢弃，并支持注入重复投递与迟到确认。
确认工作目录可写，用于生成 SQLite 状态库、结果输出与临时对象目录。

业务要求：
1. 实现 v1 与 v2 两种消息信封格式的解析与校验：v1 校验消息 ID 唯一性、投递计数为非负整数、相对过期秒数合法与正文可解码；v2 校验分片文件哈希、SQLite 元数据库中的投递代数单调性、绝对过期毫秒时间戳为非负整数与死信墓碑标记合法；畸形条目必须返回对应业务错误码并跳过而不写入任何投递状态。
2. 实现跨版本存档合并与统一投递队列构建：同一消息 ID 同时存在于两代存档时，依据存档声明的逻辑时钟与投递代数裁决最新版本，若逻辑时钟相同则按来源版本优先级裁决；合并后每条消息须保留来源版本、原始过期表示、原始投递计数与墓碑标记，且合并结果多次运行必须逐位一致。
3. 实现投递语义的模式迁移：把 v1 的相对过期秒数在注入逻辑时钟下换算为绝对过期时刻，把 v1 中无重试标签的消息迁移为 v2 的统一重试标签语义，并记录迁移映射与精度差异；迁移不得改变消息在逻辑上是否已过期，同一消息在迁移前后于同一逻辑时钟下的过期判定必须一致。
4. 实现至少一次投递与去重消费：消费者对同一消息的重复确认或迟到确认必须幂等处理，投递计数只在真正重投时递增，已确认消息不得被再次投递；每次投递、确认与重投均须记录投递代数与逻辑时钟戳，使同一消费序列在任意运行次数下产生相同投递轨迹。
5. 实现过期与死信迁移的裁决规则：在注入逻辑时钟下判定消息过期、投递代数超过上限、被消费者明确拒绝时迁移到死信并记录墓碑与触发原因；区分“已过期保留墓碑”与“已过期可物理清除”两种语义，清理水位线必须持久化且清理不得删除仍被死信审计引用的记录。
6. 实现存档整体替换的版本变化识别：收到新存档包时比较清单版本号、逻辑时钟下限与各分片哈希，判定完整替换、增量追加或无需操作；完整替换必须整体替换当前队列快照指针而非逐条覆盖，版本回退必须被拒绝或按策略降级并记录审计，替换期间已有投递状态不得丢失。
7. 实现强制终止后的恢复与并发幂等：把队列版本、迁移决策、投递代数、确认标记与清理水位线以事务原子写入 SQLite；进程被强制终止后依据持久化状态识别未提交的合并或替换步骤与半确认投递，只重放未完成步骤且不得承诺一定生成退出报告；多实例并发时同一消息同一投递代数只被提交一次，重复提交结果幂等。
8. 实现异常链路与结果验证命令行：存档缺失、JSON 行畸形、投递代数回退、摘要不匹配、逻辑时钟回拨超阈值、确认引用不存在的投递分别映射到不同业务错误码并保留可诊断字段；提供 load、consume、replace、resume、status、verify 子命令，status 以稳定排序输出每条消息来源版本、过期状态、投递代数与死信墓碑，verify 校验持久化状态与投递轨迹一致，固定样本两次运行输出完全一致。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
用本地两代存档样本验证消息加载合并、投递确认、过期死信迁移及中断恢复，核查业务错误码与两次运行结果一致。
