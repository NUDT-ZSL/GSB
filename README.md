这项新的服务端能力需要从第一行代码开始，工作目录目前没有任何已有实现或样本文件，需要在 Linux（WSL Ubuntu）上从零构建一个面向消息投递语义的领域可视化与诊断工作台。业务对象由随工程交付的固定种子脚本确定性生成：主题清单声明主题名、分区数、分区键规则与每分区积压上限；生产者事件流逐条给出事件序号、分区键、载荷摘要、注入逻辑时钟毫秒、期望投递代数与修订号；消费者订阅声明给出订阅者 ID、主题、本地回环回调端点、拉取条数与速率上限；两代投递语义快照并存，v1 为单文件 JSON 记录相对生效秒数与扁平投递依赖映射，v2 为分片 JSON 加 SQLite 元数据库记录绝对生效毫秒、语义代数、上游偏移水位依赖与失效墓碑。工作台需在可注入逻辑时钟下合并两代快照为统一投递语义视图，沿依赖边计算增量失效闭包，裁决每分区可投递水位与订阅推送补丁，并给出可复现的投递诊断、依赖失效追溯与中断恢复结论。

任务环境与准备：
Linux（WSL Ubuntu）工作目录，安装 Python 3.10+；无需外部依赖，使用标准库 sqlite3、json、argparse。
运行随题交付的固定种子脚本生成本地样本文件，包含主题清单、事件流、订阅声明与两代语义快照。
确保工作区可执行 Python 脚本，所有输入与 SQLite 数据库均生成于当前目录下。

业务要求：
1. 实现主题清单、生产者事件流、订阅声明与两代投递语义快照的解析校验，主题名与订阅者 ID 唯一，分区数为正整数，分区键规则可解析且覆盖全部事件键，事件序号严格递增，注入逻辑时钟为非负整数，v1 相对生效秒数为非负整数，v2 分片哈希与语义代数单调，任何非法输入返回明确业务错误码且不写入状态。
2. 实现两代语义快照的跨版本合并与统一投递视图构建，同一消息键在 v1 与 v2 同时存在时依据声明的逻辑时钟与语义代数裁决最新版本，逻辑时钟相同按来源格式优先级裁决，v1 相对秒数在注入逻辑时钟下换算为绝对毫秒并记录换算标度与舍入方向，合并后每个条目保留来源版本、原始时间表示与裁决依据。
3. 基于生产者事件流和统一投递视图，在注入逻辑时钟下计算每个分区的可投递水位与依赖闭包，沿消息对上游偏移水位的依赖边精确标记受影响分区，当语义补丁引入失效墓碑或代数回退时只重算受影响闭包内的水位结论，未受影响分区的既有水位与诊断结论必须保持逐位不变。
4. 实现订阅推送补丁的增量生成与依赖失效追溯，对每个订阅者只生成自上次推送游标以来新增、修改或失效的消息分组补丁，未受影响分组不得改变既有视图，同一逻辑时钟序列下重复刷新产生相同补丁序列，每条补丁包含触发语义版本、上游偏移与影响路径。
5. 在每轮逻辑时间预算与每分区并发投递上限双重约束下调度投递诊断任务，预算或并发上限不足时按订阅者优先级与稳定次序放弃剩余未启动任务并记录放弃原因，严格区分预算内未启动、启动后失败与主动放弃三类结局，已启动任务不得被截断。
6. 维护投递诊断的持久化状态与强制终止后的恢复一致性，把分区投递水位、订阅推送游标、语义版本指针、失效闭包记录与逻辑时钟水位以单事务原子写入 SQLite，进程在合并、水位计算或补丁生成中途被 SIGKILL 后，恢复路径依据持久化状态识别已提交与半提交记录，只重放缺失部分且不重复计数。
7. 实现多进程并发一致性与版本化快照整体替换，允许多个诊断实例并行处理不同订阅者，通过 SQLite 事务与文件锁保证同一分区同一语义版本只被提交一次、同一订阅游标只被推进一次，收到新语义快照包时比较版本号、代数下限与分片哈希，判定完整替换或增量追加，版本回退必须拒绝并返回独立业务错误码。
8. 提供可重复命令行接口与可视化诊断输出，支持 load、merge、diagnose、patch、resume、status、verify 子命令，status 以稳定排序 JSON 输出每分区水位、每订阅者游标、语义版本绑定与失效事件链，verify 重新运行全链并逐字段比对诊断结论，确保任意运行次序下结果逐位一致。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
本地确定性样本下合并两代语义快照并生成可复现的投递诊断与失效闭包，支持中断恢复后结果一致。
