当前是空白工作区，需要从零构建一个面向本地 Windows 环境的 GPU 调度与配额诊断工作台，聚焦 ML 训练作业在配额约束下的准入与放置决策。用户以本地 JSON 文件声明一组 GPU 资源池（每个池含卡数、单卡显存容量整数 MiB、拓扑分组标签）与一组训练作业（每个作业含显存需求曲线参数、卡数需求、配额组标识、优先级与可接受的拓扑约束）。工作台的业务核心是：在每次调度会话中，按配额组对已占用量与待调度量进行核算，把作业逐个准入到资源池并分配具体卡位，同时以确定性规则处理显存需求随数据规模（批次规模、序列长度、模型维度）变化的估算，当数据规模参数变化时重新给出估算并判定是否仍可放置。系统须维护配额核算状态、已分配卡位、被拒绝作业的原因链，并把一次完整调度会话持久化为可命名快照；用户可以修改配额、数据规模参数或池状态后继续调度，也可整体回退到任一历史快照继续。诊断工作台以 Tkinter 展示配额占用、卡位分配、需求估算与拒绝原因，并要求本地确定性样本下可重复输出一致的调度结论。

任务环境与准备：
确认 Windows 上可用 Python 3.10 及以上版本，并能导入标准库 tkinter（用于桌面诊断界面）。
安装 numpy（仅用于样本数据与整数统计计算），在项目虚拟环境中通过 pip 安装。
在项目目录内准备本地样本 JSON 清单（资源池、配额表、作业队列）与演示脚本；不依赖 GPU 硬件、真实集群、外部账号或网络服务，显存需求以参数化估算而非真实测量。
所有命令、脚本与快照文件均以 Windows 本地路径与整数业务码方式运行，日志写入本地文件。

业务要求：
1. 实现资源池与训练作业清单的加载与强校验：从本地 JSON 读取池定义与作业队列，校验池名唯一、卡数为正整数、单卡显存为正整数 MiB、拓扑分组标签合法、作业优先级为整数、卡数需求不超过所在池可分配总卡数、配额组标识必须存在于配额表；任一不合法须以 E_MANIFEST 业务码整体拒绝加载并输出具体字段位置，禁止部分加载。
2. 实现基于数据规模的显存需求估算：每个作业以批次规模、序列长度与模型维度参数推导估算显存需求（MiB 整数），估算规则须在报告中明确步骤与中间项；相同参数组合多次估算必须得到同一整数结果，估算须给出整数化的安全余量而非浮点阈值，参数越界或缺失须返回 E_ESTIMATE 并指出具体参数。
3. 实现配额组的准入核算：对每个配额组按卡总量与显存总量分别核算已占用与在途申请，作业准入须同时满足组级卡配额与显存配额；准入判定须与估算需求一一对应，被拒作业须记录触发的配额维度、当前占用、申请量与配额上限，同一输入重复核算得到一致拒绝原因链。
4. 实现带拓扑约束的卡位放置：在准入通过后为作业选择满足拓扑分组约束的连续卡位集合，放置规则须明确且稳定，不得依赖字典或哈希遍历顺序；无满足约束的连续卡位时须回退到拒绝并登记 E_PLACEMENT 原因，已放置作业的卡位在后续作业调度中必须被视为不可用。
5. 实现数据规模参数变化后的重估与重调度：用户修改批次规模、序列长度或模型维度后，受影响作业的估算需求须重新计算并重新判定准入与放置；不得保留旧参数版本下的放置结果，旧结论须标记为陈旧并在诊断输出中与当前参数版本区分，参数版本号单调递增。
6. 实现调度会话快照的版本识别与整体替换恢复：快照持久化资源池状态、配额表、作业队列、数据规模参数版本、全部放置结果与拒绝原因链；重新打开快照时须先比较快照版本与当前会话版本，若不一致须整体替换当前配额、池与放置状态而非增量合并，恢复后继续调度的结论须与快照时记录一致。
7. 实现历史调度重放校验与不可复现报告：从快照恢复后按快照中记录的参数版本重新执行一次调度，将每个作业的准入结论、分配卡位与拒绝业务码与快照记录逐项比较；若因配额上限或数据规模参数版本与快照不一致导致结论不可复现，须以 E_REPLAY 业务码报告并稳定列出首个分歧作业与分歧项。
8. 提供 Tkinter 诊断工作台与可重复演示脚本：界面须展示每个配额组的占用与上限、每个资源池的卡位占用图、每个作业的估算需求与准入结论、当前参数版本与快照列表，渲染顺序稳定；附带本地确定性样本清单与演示脚本，顺序执行首次调度、修改数据规模参数后重调度、快照恢复后重放三个场景，每个场景输出含参数版本、分配摘要与业务码的结构化总结。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。
