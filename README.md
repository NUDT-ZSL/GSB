当前是空白工作区，需要从零构建一个面向本地 Windows 环境的模型服务弹性伸缩决策工作台，聚焦 ML 推理服务的副本扩缩与并行调度。用户以本地 JSON 文件声明一个推理服务集群：每个服务含确定性负载序列（按分钟整数给出的请求数）、每副本整数并发上限、单请求整数毫秒耗时、扩缩容阈值与最小最大副本数；同时声明全局资源预算（总副本上限）与每服务并发配额。工作台按分钟推进时间轴，对每个服务依据负载与每副本并发上限计算所需副本数，在受全局副本预算与每服务配额约束下并行完成各服务的伸缩决策与请求分配，把每轮决策、副本占用与拒绝请求写入本地 SQLite 账本，并支持整轮决策的快照保存与恢复。核心技术问题是：并行调度下的预算争用、决策版本演进与恢复后逐项可复现的决策一致性。

任务环境与准备：
安装 Python 3.11 及以上版本，确认可用 sqlite3 与 tkinter 标准库模块。
安装 NumPy，用于并发调度模拟中的整数与浮点辅助计算，版本不作强制要求。
在空白工作区创建项目目录，准备本地确定性 JSON 样本声明文件与演示脚本的运行位置，不引入网络依赖。
确认执行环境为 Windows，具备可用的本地文件写入权限与回环端口使用权限。

业务要求：
1. 实现集群声明文件的加载与强校验：从本地 JSON 读取服务定义与全局预算，校验服务名唯一、负载序列为按分钟连续的非负整数、每副本并发上限与单请求耗时为正整数、最小副本数不大于最大副本数、全局总副本上限为正整数；任一不合法须以 E_DECL 业务码整体拒绝加载并输出出错字段路径。
2. 实现按分钟推进的副本需求估算：对每个服务依据该分钟请求数与每副本并发上限按整数规则推导所需副本数，并夹在最小与最大副本数之间；估算须输出中间项（请求数、每副本可承载量、未夹取需求），相同声明与分钟多次估算必须得到同一整数结果，需求无法确定时须返回 E_DEMAND 并标注缺失输入。
3. 实现并行估算与统一裁剪提交的调度边界：各服务的副本需求可并行计算，但最终分配须在统一裁剪阶段提交，保证任一分钟全部服务分配副本数之和不超过全局总副本上限且每服务分配不超过其并发配额；裁剪规则须确定且不依赖服务处理先后，被裁服务须记录触发维度与裁剪前后副本数，不得出现并发估算突破全局预算的最终结果。
4. 实现请求分配与拒绝量核算：按最终分配副本数与每副本并发上限计算该分钟可承载请求量并分配到各服务，超出的请求计入拒绝量；分配、可承载量与拒绝量须与同分钟的需求估算记录、最终副本数逐项自洽，拒绝量不得为负且不得大于请求数，任何不自洽须以 E_ALLOC 报告并定位到服务与分钟。
5. 实现声明版本演进与陈旧结论失效：声明文件被修改后版本号单调递增，此前轮次的决策结论须被标记为陈旧且不得参与当前汇总，新一轮推进须整体替换旧结果的展示与账本当前视图而非逐分钟增量合并；替换时须稳定列出受影响的服务、分钟范围与版本差异。
6. 实现决策账本持久化与强制终止后的恢复：每完成一个分钟须把该分钟决策、副本占用与拒绝量写入本地 SQLite 账本并记录声明版本与分钟进度，进程被强制终止后重启只能依据已持久化的完整分钟恢复，未完成分钟须标记为未知并要求重跑，不得声称能生成退出报告，恢复报告须列出已恢复分钟数与未决分钟。
7. 实现恢复后的一致性重放校验：从快照或账本恢复后按记录的声明版本与负载重新推进已完成分钟，将每服务的需求估算、最终分配、拒绝量与裁剪原因与账本逐项比较，差异须定位到首个不一致的分钟、服务与字段并输出 E_REPLAY；因声明版本或负载序列不一致导致不可复现时须在报告中说明具体依据。
8. 提供 Tkinter 决策工作台与可重复演示脚本：界面展示每分钟各服务副本需求与最终分配、全局预算占用曲线、拒绝量与被裁服务原因、当前声明版本与快照列表，渲染顺序稳定；附带确定性样本负载与演示脚本，顺序执行基准负载全量推进、修改并发上限后重推进、快照恢复重放三个场景并输出稳定顺序的决策总结。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
本地样本验证全量推进、预算裁剪与快照恢复重放的决策逐项一致，并检查异常业务码。
