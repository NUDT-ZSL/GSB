当前是空白工作区，需要从零实现一个本地消息投递网关的投递追平与配额令牌账本组件，核心业务问题不是跨版本信封互操作，而是：消费端在限速配额约束下追平积压消息时，如何以可复现的令牌账本裁决每一次投递尝试，并保证配额消耗、投递代数与死信判定在中断恢复与多进程并发下不重不漏。本地 JSON 样本给出：主题与分区清单（主题名、分区数、分区键规则、分区积压上限）、消费者租约声明（消费者 ID、订阅主题、每次投递请求的消息条数、消费速率上限条每秒、每次投递的逻辑超时预算）、以及配额配置（全局限速令牌桶容量与补充速率、每消费者令牌桶容量、每轮追平逻辑时间预算、投递代数上限与重试退避基数）。消息本身由本地确定性生成器按分区键与全局种子产出，不含需要跨版本转换的字段；所有时间判定只依赖可注入逻辑时钟毫秒值，不读取系统墙钟。两个网关工作进程与重复启动的恢复实例会共享同一份 SQLite 持久化状态。

任务环境与准备：
安装 Python 3.11 及以上版本，并确认可用的包安装方式
安装 SQLite 命令行工具，确认工作区可创建本地数据库文件、临时文件与锁文件
在本地工作区准备确定性消息样本生成所需的主题分区清单、消费者租约与配额配置 JSON 文件
准备可注入逻辑时钟的配置样本与包含受控异常条目的注入清单
确认可同时启动两个网关进程与一个恢复进程用于并发验证

业务要求：
1. 实现主题分区清单、消费者租约与配额配置的解析校验：主题名与消费者 ID 唯一、分区数为正整数、分区键规则可解析、消费速率上限与桶容量为正整数、补充速率为有限正数、每轮追平逻辑时间预算与逻辑超时预算为正整数、投递代数上限非负；非法输入必须返回不同业务错误码且不写入任何持久化状态。
2. 实现基于注入逻辑时钟的全局与每消费者双层令牌桶账本：每次投递尝试前按补充速率与上次补充时刻计算两层新增令牌，令牌余额与上次补充时刻须在扣减令牌的同一事务内更新；令牌不足时必须延迟投递而非拒绝消息，并记录所需等待逻辑时长与当时的桶水位，同一逻辑时钟序列下重复运行必须得到逐位一致的令牌账本。
3. 实现配额约束下的投递追平调度：每轮从各分区按顺序取至多消费者请求条数的消息尝试投递，同时受双层令牌余额、每轮追平逻辑时间预算与每次投递逻辑超时预算约束；预算耗尽必须停止本轮并保留未投递消息，区分预算内未启动、投递中失败与主动放弃三类结局，已启动投递不得被事后标注为超时。
4. 实现投递代数演进与幂等确认：每次成功投递递增该消息投递代数，重复确认、迟到确认与跨消费者确认必须幂等且不得使代数回退或重复递增，已确认消息不得再次进入待投递队列；同一消费序列在任意运行次数下产生逐位一致的投递轨迹与代数序列。
5. 实现投递失败的重试退避与死信迁移裁决：失败按重试退避基数与当前投递代数计算下一次可投递逻辑时刻并施加确定性抖动与上限，代数超过上限时迁移死信并记录触发原因（失败、拒收、过期）与墓碑；退避计算与配额补充必须分别记账，不得以退避等待抵扣令牌消耗。
6. 实现令牌账本与投递状态的持久化及强制终止后的恢复：把队列版本、每消息投递代数与可投递时刻、双层桶余额与上次补充时刻、确认标记、死信墓碑与逻辑时钟水位以事务原子写入 SQLite；进程在扣减令牌、递增代数或迁移死信中途被强制终止后，恢复路径只重放未完成步骤，已扣令牌不得重复扣减、已投递消息不得重复递增代数。
7. 实现多进程并发一致性与配额不超卖：多个网关进程与恢复实例共享同一持久化状态时，通过 SQLite 事务与文件锁保证同一消息同一代数只被投递一次、全局令牌桶不被并发超扣、死信墓碑只被写入一次，重复提交相同投递请求必须幂等；读取方只能看到完整已提交的队列版本与桶水位。
8. 实现异常链路与结果验证命令行：主题不存在、消费者租约缺失、令牌桶配置版本回退、投递引用不存在消息、确认引用不存在的投递、逻辑时钟回拨超阈值分别映射到不同业务错误码并保留可诊断字段；提供 load、deliver、resume、status、verify 子命令，status 以稳定排序 JSON 输出各主题积压量、各消费者令牌余额与预算消耗、消息最大投递代数与死信数，verify 校验持久化状态与实际逐条重放结果的代数与桶水位一致。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。
