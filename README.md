当前是空白工作区，需要从零实现一个本地应急预案演练与异常注入验证工作台，交付领域可视化与诊断工作台。业务目标是让每一次演练的步骤推进、故障注入、超时判定与恢复裁决都在可注入逻辑时钟下可复现、可追溯、可校验。演练剧本以本地 JSON 给出：预案清单（预案名、步骤序号、步骤依赖的前置步骤、每步骤的期望观测事件、超时逻辑毫秒、是否允许跳过）、本地可编程 HTTP 测试服务描述（被演练系统按路径返回状态码、延迟、畸形响应与断开连接）以及逻辑时钟步进表与注入清单（在指定逻辑毫秒于指定步骤注入网络中断、服务拒绝、数据损坏、时钟回拨）。工作台需按依赖关系推进演练步骤，在逻辑时钟下统计每步骤的观测结果与超时状态，按注入清单在真实调用路径上触发异常，并在进程被强制终止后依据持久化状态恢复演练并给出恢复裁决；全部判定只依赖注入的逻辑时钟，不读取系统墙钟。

任务环境与准备：
确认 Windows 上可用 Python 3.11 或以上；本地回环 HTTP 测试服务使用标准库 http.server 实现，不引入额外第三方依赖。
在工作区创建固定本地样本目录：预案清单 JSON、测试服务路由描述 JSON、注入清单 JSON 与逻辑时钟步进表，全部为确定性内容并附内容摘要。
准备本地 SQLite 状态库路径与临时对象目录，确保多次运行可清空后从同一初始状态开始，不依赖真实账号、线上站点或外部服务。
编写演示脚本入口（如 run_demo.py）串联 load/run/inject/resume/status/verify，保证在 Windows 命令行下可直接执行并输出稳定排序 JSON。

业务要求：
1. 实现预案清单、测试服务描述与注入清单的解析校验：预案名与步骤序号唯一、前置步骤存在且依赖无环、超时逻辑毫秒为正整数、期望观测事件枚举合法、注入清单引用的步骤存在且注入逻辑时刻落在该步骤的演练时间窗内；非法输入必须返回明确业务错误码（如 E_BAD_PLAN、E_CYCLE、E_BAD_INJECT）且不写入任何持久化状态。
2. 实现演练步骤的依赖推进与状态机演进：步骤在待执行、执行中、已观测、超时、已跳过、已中止之间按规则迁移，只有全部前置步骤达成已观测或已跳过才可推进后继步骤；迁移必须依据持久化的前置步骤结论与逻辑时钟裁决，重启后不得凭内存残留决定步骤是否已完成。
3. 实现注入异常的观测分类与异常链路隔离：被演练系统的连接拒绝、响应超出单步骤超时预算、响应状态码不符合期望、响应体畸形、注入的数据损坏分别映射到不同业务错误码并在观测记录中保留可诊断字段（步骤、尝试序号、注入时刻）；单个步骤异常不得污染其他步骤的已提交观测结果或中断主推进循环。
4. 实现基于注入逻辑时钟的超时判定：步骤超时由注入逻辑毫秒值与步骤开始时刻之差判定，不得读取系统墙钟；超时须由真实等待计时与主动中止共同实现而非事后标注，被超时的步骤必须显式区分“尚未启动”“已启动后超时”“主动跳过”三类结局，且同一逻辑时钟序列下重放必须得到逐位一致的结局序列。
5. 实现演练轮次的整体替换与版本变化识别：每次预案或注入清单提交产生新版本号并比较内容摘要、步骤集合与注入条目摘要，判定完整替换、增量追加还是无需操作；整体替换须以临时表加版本号切换当前演练快照指针而非逐条覆盖，版本回退必须被拒绝并返回业务错误码，进行中的步骤必须绑定其开始时的版本直至结束。
6. 实现强制终止后的恢复裁决：把演练版本指针、已提交步骤结局、观测记录摘要、注入消费水位与逻辑时钟水位以单事务原子写入 SQLite；进程在步骤执行或注入触发中途被强制终止后，恢复路径须识别已提交步骤与半提交步骤，只重放未完成步骤且不得重复消费注入条目或重复累计超时计数，恢复后状态与未中断运行逐字段一致。
7. 实现多进程并发一致性与幂等提交：允许多个演练实例并行推进同一预案的不同分支，通过 SQLite 事务与文件锁保证同一步骤同一版本只被推进一次、同一注入条目只被消费一次，重复提交相同步骤结局必须幂等；读取方只能看到完整已提交的步骤结局而非中间态，被锁占用时须以业务错误码而非静默等待处理。
8. 提供命令行接口与诊断可视化输出：支持 load、run、inject、resume、status、verify 子命令，status 以稳定排序 JSON 输出每步骤阶段、结局分类、注入消费状态与逻辑时钟当前位置，verify 校验持久化状态与观测记录摘要的一致性；使用本地固定样本演示脚本执行两次运行产生完全一致的输出。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
使用本地固定样本演示演练推进、异常注入与强制终止后恢复，两次运行输出一致且快照整体替换可识别版本回退。
