在空白工作区从零实现一个本地配置中心热更新引擎及其数据处理管线与结果验证工具。配置中心以本地 JSON 文件提供初始配置快照，包含命名空间、配置键、值、版本号与逻辑时钟戳；若干本地数据处理客户端订阅配置并执行确定性计算任务，任务输出受配置参数影响。配置中心通过本地 HTTP 接口接收配置补丁，补丁需在指定逻辑时钟窗口内生效，客户端必须原子地观察到新配置版本，不得读到新旧混合参数导致计算结果不一致。引擎需维护配置版本链，记录每次热更新对客户端计算结果的依赖关系，并提供验证工具复现任意版本下的计算结果。所有时间推进基于可注入的逻辑时钟，不依赖系统墙钟；进程可能被强制终止，恢复后需保证配置与结果管线一致。

任务环境与准备：
安装 Python 3.10 及以上版本，并确保 pip 可用；执行 pip install flask 安装本地 HTTP 接口依赖。
准备本地样本目录：包含初始配置快照 config_snapshot.json、补丁文件 patch_*.json、数据处理客户端输入样本 input_records.json 与容差配置文件。
确认 SQLite 可用（Python 标准库 sqlite3 即可），工作目录具备读写权限以创建配置版本数据库与结果文件。
无需外部网络、真实账号或容器环境；本地 HTTP 服务仅监听回环地址用于补丁提交与状态查询。

业务要求：
1. 实现配置快照与补丁的解析校验：读取本地 JSON 配置快照，校验命名空间唯一、配置键格式合法、值类型与声明类型一致、版本号严格递增、逻辑时钟戳非负；补丁需声明目标版本号、内容摘要与生效逻辑时钟窗口，非法输入必须返回明确业务错误码（如 E_BAD_CONFIG、E_BAD_PATCH、E_VERSION_CONFLICT）且不修改当前配置状态。
2. 实现配置版本链与原子热更新：每次补丁提交产生新版本并整体替换当前配置快照指针，旧版本保留用于回放；提交必须在 SQLite 事务中完成，写入版本号、内容摘要、生效逻辑时钟与父版本号，客户端读取时必须看到某个完整版本而非更新中间态，同一补丁重复提交必须幂等且返回相同版本号。
3. 实现基于注入逻辑时钟的补丁生效窗口控制：补丁只在生效逻辑时钟窗口内被应用，窗口边界由逻辑时钟毫秒值判定，不读取系统墙钟；逻辑时钟回拨超过配置容差时补丁必须被拒绝并返回业务错误码，同一逻辑时钟序列下重复提交必须得到逐位一致的生效序列。
4. 实现数据处理客户端的确定性计算管线：客户端订阅配置版本并执行固定计算任务（由配置参数决定过滤阈值、聚合权重与输出格式），计算顺序与浮点运算顺序固定，使相同配置版本与相同输入样本在任意运行次数下产生逐位一致的结果；客户端必须记录本次计算绑定的配置版本号与内容摘要。
5. 实现热更新期间客户端计算结果一致性保障：客户端在计算中途收到新配置版本时，必须完成当前版本计算并记录结果对应版本，不得中途切换参数；新配置仅在下一次计算开始时生效；若同一客户端并发收到多个补丁，需按逻辑时钟与版本号裁决最终生效版本，输出结果与版本绑定关系供验证工具核对。
6. 实现配置版本与计算结果的持久化及强制终止恢复：把当前配置版本指针、补丁审计记录、客户端已提交计算结果摘要与逻辑时钟水位以事务原子写入 SQLite；进程在补丁提交或客户端计算中途被强制终止后，恢复路径识别未提交补丁与半提交计算结果，只重放未完成步骤，不得出现配置已更新而结果仍绑定旧版本却标记为已提交的状态。
7. 实现多进程并发一致性与幂等：允许多个客户端进程与配置更新进程并行，通过 SQLite 事务与文件锁保证同一版本号只提交一次、同一客户端同一计算轮次结果只提交一次，重复提交相同补丁或计算结果必须幂等；读取方只能看到完整已提交配置版本而非更新中间态，且不得因并发写导致版本链断裂。
8. 提供数据处理管线与结果验证工具：支持 serve、apply、compute、resume、status、verify 子命令，status 以稳定排序 JSON 输出当前配置版本、逻辑时钟水位与各客户端绑定版本，verify 校验持久化状态与计算结果版本绑定的一致性，并支持按指定版本回放计算结果以核对差异；使用固定本地样本运行两次输出完全一致。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
使用本地样本验证补丁原子生效、客户端结果与配置版本绑定一致，以及强制终止后恢复状态正确。
