当前是空白工作区，需要从零实现一个本地增量物化视图引擎，核心业务目标是让两代物化视图定义与增量日志格式在同一套刷新链路中互操作，并在版本演进中保持视图结果与增量可合并语义一致。本地样本以目录形式给出：v1 视图定义为单文件 JSON，记录视图名、基表名、过滤与聚合表达式、相对刷新秒数与一个扁平基表到视图的映射；v2 定义使用分片 JSON 加 SQLite 元数据，记录视图规范名、基表集合、增量聚合规则、绝对刷新时刻毫秒、视图代数、上游视图依赖列表与失效墓碑。另有一组按逻辑时钟递增的基表变更日志段（JSON 行格式，含变更序号、基表名、行键、变更前后镜像与内容摘要）与若干历史视图快照。引擎需读取并合并两代定义构建统一视图索引，按变更日志做增量刷新，支持查询与快照整体替换，并识别版本变化。全部资源量、时间戳与聚合结果均以本地确定性样本为准，不依赖外部服务或真实数据库实例。

任务环境与准备：
在 Windows 上准备 Python 3.11 及以上版本，创建并激活本地虚拟环境（不推荐全局安装）。
安装 NumPy 与 pytest 到该虚拟环境，版本以安装时可得的最新稳定版为准，并确认 python -m pytest --version 可用；SQLite 使用 Python 内置 sqlite3 模块，无额外服务依赖。
在工作区准备本地样本目录：两代视图定义样本、按逻辑时钟递增的基表变更日志段、若干历史视图快照，全部由脚本确定性生成，不含真实账号或线上数据。
确认工作区无既有项目代码与数据附件，所有目录与文件均由本题从头创建；不引入 Docker 或容器环境。

业务要求：
1. 实现两代物化视图定义与变更日志段的解析校验：v1 校验视图名唯一、基表引用存在、聚合表达式列引用合法、相对刷新秒数为非负整数、扁平映射与基表声明一致；v2 校验分片文件哈希、SQLite 元数据中视图代数单调、绝对刷新时刻为整数毫秒、上游视图依赖两端闭合且无环、失效墓碑与视图状态相容；非法定义或日志段须返回明确业务错误码，且不得写入任何持久化产物。
2. 实现跨版本定义合并与统一视图索引构建：同一视图在两代定义中同时存在时，依据定义声明的逻辑时钟与视图代数裁决最新版本，逻辑时钟相同则按来源格式优先级裁决；合并后每个视图须保留来源版本、原始刷新时间表示与裁决依据，冲突裁决过程须可追溯，且重复合并相同输入必须得到逐位一致的索引摘要。
3. 实现刷新时间与增量聚合语义的模式迁移：v1 缺失绝对刷新时刻的视图在注入逻辑时钟下换算为绝对刷新时刻并记录换算标度与舍入方向，v1 无视图代数与上游依赖的视图迁移为 v2 统一语义并记录迁移映射；迁移不得改变视图在同一逻辑时钟下是否已到期与结果是否可见的判定。
4. 实现基于变更日志的增量刷新：按变更序号顺序把基表行的插入、更新、删除应用到视图的聚合状态，维护计数、求和、平方和与可见行集合，流式聚合顺序与浮点运算顺序固定使结果逐位可复现；增量刷新结果必须与从空状态全量重放同一日志链得到的结果逐条一致，不一致须输出首个差异行与来源日志段。
5. 实现上游视图依赖的增量失效传播：某基表变更或上游视图刷新产生新结果时，沿视图依赖图计算受影响闭包，精确标记哪些下游视图的聚合状态需要重新计算、哪些可安全复用，未受影响视图不得被重算且其查询结果必须保持不变，失效决策须输出触发来源与传播路径。
6. 实现刷新时间快照整体替换与版本变化识别：收到新定义包或新日志包时比较清单版本号、视图代数下限、各分片哈希与定义摘要，判定完整替换、增量追加还是无需操作，完整替换须以临时表加版本号整体切换当前定义指针而非逐条覆盖；版本回退必须被拒绝并返回业务错误码，替换后未受影响视图的聚合状态不得被重算。
7. 实现持久化状态与强制终止后的恢复：把视图代数指针、已应用日志水位、各视图聚合状态摘要、迁移决策与逻辑时钟水位以事务原子写入 SQLite；进程在增量刷新或定义替换中途被强制终止后，恢复路径依据持久化状态识别已提交变更与半提交状态，只重放未完成变更，不得重复累加聚合状态或回退已提交结果。
8. 实现多进程并发一致性、幂等提交与可重复命令行演示：允许多个刷新实例与查询实例并行，通过 SQLite 事务与文件锁保证同一变更序号同一视图代数只被应用一次、重复提交相同变更或相同替换请求必须幂等，读取方只能看到完整已提交的视图版本；提供 load、merge、refresh、query、replace、resume、status、verify 子命令，status 以稳定排序 JSON 输出视图代数、各视图已应用日志水位与迁移决策数量，演示脚本使用固定本地样本两次运行输出逐字一致。
