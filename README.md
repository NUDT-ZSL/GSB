在空白工作区从零实现一个本地顺序消息中间件的分区投递与事务提交引擎，用于在确定性样本上复现顺序消费、事务消息两阶段提交、故障注入与中断恢复的完整链路。本地 JSON 样本给出：主题与分区清单（主题名、分区数、每分区顺序键规则、分区日志容量）、生产批次（批次序号、主题、顺序键、事务 ID、消息载荷、逻辑时钟毫秒戳），以及引擎配置（每分区单批最大条数、事务超时逻辑毫秒、重试预算、注入清单路径）。引擎需要把消息按顺序键路由到分区并追加到分区日志，保证同一顺序键在同一分区内严格有序；对声明事务的批次执行预备与提交两阶段流程，未提交事务的消息不得对消费者可见；消费者按分区顺序拉取并确认偏移，确认必须幂等且偏移只能单调前进。引擎还需支持按注入清单在追加、预备、提交、消费确认四个阶段注入受控异常，并在进程被强制终止后依据 SQLite 持久化状态恢复，只重放未完成步骤。全部行为基于注入的逻辑时钟，不读取系统墙钟。

任务环境与准备：
安装 Python 3.11 或以上，并确认 sqlite3 标准库可用（无需额外服务）。
安装 pytest（用于本地验证脚本的可选依赖）并确认命令行可执行。
在任务目录下准备固定本地 JSON 样本与注入清单，所有文件由题目描述构造，不依赖网络、账号或外部中间件。
确认运行环境允许本地文件锁与多进程启动，且工作目录可写。

业务要求：
1. 实现主题、分区与生产批次的解析校验：校验主题名唯一、分区数不超过配置上限、顺序键规则可解析、批次序号严格递增、事务 ID 与批次的事务声明一致、消息载荷可解码，构建分区路由模型；非法输入必须返回明确业务错误码且不写入任何持久化状态。
2. 实现按顺序键的分区路由与分区日志追加：同一顺序键必须始终路由到同一分区，分区日志按追加顺序记录批次序号、偏移、载荷摘要与逻辑时钟戳；相同输入重复加载必须得到逐位一致的分区日志与偏移分配，顺序键跨分区不得出现乱序接受。
3. 实现事务两阶段流程与消费者可见性：事务批次先进入预备态并写入分区日志占位，提交后才对消费者可见，回滚或超时未提交的占位必须标记为不可见墓碑；事务状态迁移只能依据持久化的前置状态裁决，超时判定以事务超时逻辑毫秒与注入逻辑时钟计算，不得凭内存残留决定是否已提交。
4. 实现分区顺序消费与幂等偏移确认：消费者按分区顺序拉取已提交消息并回报确认，确认必须校验消费者身份与消息所属分区偏移，重复确认与迟到确认必须幂等，偏移只能单调前进且不得跳过未提交消息；同一拉取序列在任意运行次数下产生逐位一致的投递记录。
5. 实现注入清单驱动的受控异常与业务错误码：按本地注入清单在追加、预备、提交、消费确认四阶段注入受控异常（追加时分区日志写满、预备时事务 ID 冲突、提交时摘要不匹配、确认时偏移回退），每种异常映射到不同业务错误码并保留可诊断字段；注入不得修改样本文件，单个异常不得污染其他分区已提交状态。
6. 实现强制终止后的恢复与半提交事务清理：把事务阶段、分区日志水位、已提交偏移、占位可见性与逻辑时钟水位以事务原子写入 SQLite；进程在任意阶段被强制终止后，恢复路径依据持久化状态识别已预备未提交事务与未完成确认，只重放未完成步骤并清理无引用占位，不得承诺一定生成退出报告。
7. 实现多进程并发一致性与幂等提交：允许多个生产与消费实例并行操作同一主题的不同分区，通过 SQLite 事务与文件锁保证同一顺序键同一批次只被追加一次、同一事务只被提交一次、同一偏移确认只被记录一次；读取方只能看到完整已提交事务的消息，不得观察到预备中间态。
8. 提供命令行接口与可重复验证工具：支持 load、produce、commit、consume、resume、status、verify 子命令，status 以稳定排序 JSON 输出每分区偏移水位、可见消息数、墓碑数与未完成事务数，verify 校验持久化状态与分区日志摘要一致；使用固定本地样本与注入清单运行两次，输出必须完全一致。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
使用固定本地样本与注入清单验证分区顺序、事务可见性、异常错误码及强制终止后恢复结果一致。
