即时通信与音视频会议平台的值班 SRE 在结束一次线上处置后，要把告警、发布、探测与值班交接备注整理成一份能在下一次交接里直接使用的故障事件时间线。会议入会、媒体转发、信令路由与消息投递四类服务共用一份依赖登记，故障期间告警风暴会同时打出几十条同类记录，发布与回滚又夹在告警之间，单看某一条记录无法判断这次故障从哪里开始、到哪里结束。平台需要一套本地可重复运行的事件汇总组件，把多源事件按逻辑时刻与服务标识归一，压缩为按故障聚合的时间线，并给出可交接的摘要和数量账目，让复盘人员能追溯到每个故障的影响面与剔除依据。

任务环境与准备：
准备 Linux（WSL Ubuntu）下的 Python 3 运行环境，只使用标准库，SQLite 通过 Python 标准库 sqlite3 访问，不需要额外安装第三方包或启动外部数据库服务。
在工作区创建项目目录，放置依赖登记文件、固定种子事件样本生成脚本、事件输入样例与运行说明，命令行入口使用 argparse 声明事件文件路径、依赖登记路径、SQLite 路径与增量批次参数。
准备本地运行步骤：先生成固定种子事件样本，再执行一次全量汇总并把结果写入 SQLite，随后追加一个新批次执行增量重算，最后导出时间线与数量账目供比较。

业务要求：
1. 读取按逻辑时刻记录的多源事件文件，每条事件至少包含来源类型（告警、发布、探测、值班备注、用户投诉）、服务标识、事件码与毫秒级逻辑时刻，把不同来源统一为带来源类型、服务标识与规范化时刻的事件序列，并校验服务标识都出现在依赖登记中，出现未登记服务时给出可定位的错误而不是静默丢弃。
2. 按服务标识与时间邻近性对事件聚类：同一服务在邻近窗口内的事件归入同一候选簇，候选簇之间若至少一条事件的时间差不超过窗口阈值且存在依赖关联，则合并为同一故障事件簇，合并过程要输出每次合并涉及的两个簇编号与依据，保证聚类结果可复核。
3. 对故障事件簇判定起止边界：以簇内最早与最晚事件的逻辑时刻为初值，结合告警恢复事件与探测恢复记录修正结束时刻，若簇内只有触发没有恢复则标记为未闭环并写入摘要，不能把未闭环故障的结束时刻伪造成观测窗口末端。
4. 识别每个故障事件簇的根因候选服务与受影响下游服务集合：按依赖登记的传递闭包计算下游集合，结合簇内最早出现异常的告警与探测事件的来源服务给出根因候选排序，受影响集合只包含确实在依赖链上的服务，不把无依赖关系的服务计入影响面。
5. 对重复与噪声事件做剔除：同一服务同一事件码在告警风暴窗口内的重复触发按首次保留、后续计入重复计数并记录剔除依据，值班备注与用户投诉不做去重但可标注为佐证事件，剔除结果要保留原始事件编号以便追溯。
6. 输出压缩前后的数量账目：按来源类型与按服务分别给出原始条数、去重后条数、被压缩进各故障簇的条数与佐证事件条数，账目合计必须与输入总条数一致，任何一类的差额都要能由剔除记录解释。
7. 按逻辑时刻生成故障事件时间线，按簇排序并标注每簇的起止时刻、涉及服务、影响面摘要与关键事件，关键事件的选择依据要写进时间线条目，时间线在合并后的簇上不得出现时间倒序或簇范围重叠的矛盾。
8. 把故障事件簇、时间线与摘要报告持久化到 SQLite，支持在事件文件追加新批次后按受影响服务增量重算时间线，增量结果与全量重算在未受影响簇上的时间线与账目逐字段一致，并能在重算后识别出边界发生变化的簇。

验收：
用固定种子的事件流与人工标注故障真值对比，验证聚类边界、影响面、账目一致与增量重算结果一致。
