当前是空白工作区，需要从零构建一个面向本地 Windows 环境的主从复制延迟观测与多版本格式互操作编辑台，属于数据库方向。系统以本地 SQLite 文件持久化主库操作日志与从库回放进度，用户在 Tkinter 界面或脚本中录入一段确定性的写入操作序列，系统按主库提交序号、逻辑时钟毫秒值与事务标识生成主库日志记录，再由模拟从库按可配置的回放速率与并发回放度逐条回放，实时估算复制延迟。日志记录存在三种历史格式版本：v1 只含提交序号与事务标识，v2 增加毫秒级提交时间戳与事务大小，v3 再增加日志段标识与段内偏移。系统须在三种版本间互操作：读取并升级旧格式日志段，以当前版本写入新记录，同时保证延迟估算在格式升级、回放中断与强制终止后仍可复现；并把一次完整观测会话（日志段集合、从库回放进度、延迟样本序列与估算参数）快照持久化，恢复时识别版本差异并整体替换而非增量合并。

任务环境与准备：
安装 Python 3.11 或以上，确认 tkinter 可用（Windows 官方安装包默认包含）。
无需第三方包，SQLite 使用标准库 sqlite3；如使用其他依赖请在项目内声明版本。
准备本地确定性样本操作序列与演示脚本，不依赖任何线上服务或真实账号。
在工作区根目录创建项目结构，日志段、快照与检查点文件均存放在本地目录。

业务要求：
1. 实现主库操作日志的三版本记录编解码与段文件格式：每条记录采用长度前缀编码，头部含整数格式版本号、提交序号、事务标识；v2 增加毫秒提交时间戳与事务大小字节数，v3 再增加日志段标识与段内偏移；解码时校验长度自洽、提交序号严格递增、版本属于受支持集合，非法记录须以 E_FORMAT 业务码报告出错段与偏移，合法记录须能在 v1、v2、v3 间无损解析并保留原始版本标记。
2. 实现从库回放模拟器与延迟观测采样：模拟从库按可配置的回放速率（事务每秒整数）与并发回放度逐条回放日志，每条记录回放完成时记录回放完成的逻辑时钟毫秒值；复制延迟定义为同一提交序号在主库提交时间戳与从库回放完成时间戳之差，时间基准统一为单调计数的逻辑时钟毫秒，须明确声明时钟来源与观测方式，回放未完成或缺少提交时间戳的记录须标记为延迟未知而非填零。
3. 实现延迟估算的定点数值与误差传播：延迟样本序列的均值、P95 与最大延迟须以整数定点表示并给出量化误差上界，回放速率与并发度作为整数参数参与推导其对延迟估算偏差的影响；当样本数不足或存在未知延迟记录时须按显式规则给出估算状态与置信标记，不得静默剔除未知样本，误差界的推导步骤须写入观测报告。
4. 实现格式升级与旧版日志段互操作：打开日志目录时检测全部段文件的格式版本，低于当前版本的段须在内存中完成记录级升级并以当前版本重写为新段，旧段保留为只读备份；升级每段完成后更新检查点文件，强制终止后重启须依据检查点判断哪些段已完成升级并继续剩余部分，不得把半升级段当作已完成；无法升级的记录须以 E_FORMAT 保留在原段并列入升级报告。
5. 实现回放进度的持久化与强制终止后的恢复：回放进度须持久化已回放到的提交序号、并发回放中已完成与未完成的批次标记以及累计延迟样本；进程被强制终止后重启只能依据持久化状态恢复，不得声称能生成退出报告，未完成批次须标记为未知并要求重放，重放不得重复计入已确认的延迟样本，且恢复报告须列出已恢复序号、未知批次数量与重建的样本计数。
6. 实现延迟估算会话快照的版本识别与整体替换恢复：快照持久化日志段集合摘要、每段格式版本、回放进度、延迟样本序列与估算参数版本；重新打开快照时须先比较快照中的段集合摘要与格式版本集合与当前磁盘是否一致，若不一致须整体替换当前日志视图、回放进度与样本状态而非增量合并，且快照之间的版本差异与变更段须可稳定辨识。
7. 实现历史观测重放校验与不可复现报告：从快照恢复后按快照记录的回放速率与并发度重新回放日志并重新聚合延迟样本与估算结果，与快照保存的样本序列和统计量逐项比较；因回放速率参数、段格式版本或段集合不一致导致不可复现时须以 E_REPLAY 业务码报告并说明具体不一致项，逐项一致的须输出稳定顺序的比对摘要。
8. 提供 Tkinter 交互界面与可重复演示脚本：界面展示日志段列表与格式版本、从库回放进度、延迟样本分布、当前估算统计与误差界、估算参数版本与快照列表，渲染顺序稳定；附带确定性样本操作序列与演示脚本，顺序执行冷启动回放观测、格式升级后重新观测、强制终止后恢复并重放校验三个场景，每个场景输出包含版本集合、样本计数与估算结论的观测报告。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
用本地样本验证三版本日志互操作、延迟估算与终止后恢复重放结果一致及业务码。
