城市公共交通服务部门在早晚高峰上线了一批面向市民的出行问询服务，问询内容混合了固定话术的线路查询、时变的绕行建议与需要现场推断的换乘组合三类，服务团队计划用小模型起草候选 token、再由目标模型一次批量验证来压低响应时间。高峰时段问询密度是平峰的数倍，上下文既有几乎可复制的固定模板，也有需要重新推断的开放描述，草稿接受率在两者之间大幅摆动：固定候选长度与固定接受阈值在模板类请求上验证白跑，在开放类请求上又频繁回退重采样，值守的推理服务运维工程师无法说明这套投机策略在当前负载下究竟是否划算，也说不清参数调到多少才合适。团队需要在普通开发机上搭一套可反复重放的本地核验组件，把逐轮草稿生成、逐位置接受判定、首拒绝位置回退重采样、逐请求统计与延迟预算对照串成同一条可核对的链路，并能在候选长度与接受阈值调参后独立复算、给出可比较的策略结论。

任务环境与准备：
准备 Linux（WSL Ubuntu）上的 Python 3 运行环境，仅使用标准库，不安装第三方包。
在工作目录中创建项目，样本由程序自带的确定性生成器产出，不依赖真实模型服务、显存或线上资源。
使用 Python 标准库 sqlite3 保存已提交请求的判定与统计结果，运行方式与参数说明随项目给出。

业务要求：
1. 实现一个按固定种子产出的确定性生成器，构造若干模型副本声明（草稿模型与目标模型的词表映射、特殊 token 约定、每 token 前向耗时基线）、一条按逻辑时刻到达的出行问询请求流（提示 token 序列、最大生成 token 数、截止时刻、租户归属）以及一组投机策略声明（候选长度、接受阈值、回退规则、延迟预算）；同一工程须以三个 schema 版本描述同一内容，版本差异体现在字段命名、时刻与预算单位（tick 与毫秒）、阈值刻度（千分比与万分比）以及候选长度表达方式上。
2. 装载阶段须把每个请求的提示 token 序列归一为草稿模型与目标模型都能识别的内部词表序列，对因词表映射差异而无法对应的 token 明确给出不可映射位置与请求级标记，并输出每个请求的参数摘要；归一后的序列长度与特殊 token 位置须与生成器记录的真值逐项一致。
3. 对每个请求按投机策略逐轮生成草稿候选 token 序列，草稿生成只依据当前上下文与草稿模型的确定性打分，并记录每轮草稿长度、逐 token 的草稿打分及所在目标词表位置；同一请求在同一策略下的草稿序列须两次重放完全一致。
4. 将草稿候选序列提交目标模型做一次批量验证，对每个候选位置比较目标模型与草稿模型在该位置的 token 分布并依据接受阈值输出接受或拒绝判定；当两个分布在某位置完全相同时该位置必须判定为接受，判定依据须逐位置记录以备核对。
5. 在首个拒绝位置由目标模型重采样出正确 token，截断该位置之后的全部草稿候选并回退到该位置继续下一轮，输出最终接受 token 序列与逐次回退重采样记录；达到最大生成 token 数或截止时刻时须正常结束并标注结束原因。
6. 逐请求统计草稿 token 数、接受 token 数、验证批次耗时与回退次数，据此计算接受率与相对逐 token 解码的加速比，并与延迟预算比对，标记超限请求及导致超限的具体轮次与判定依据；统计值须与逐轮记录的聚合结果完全一致。
7. 在同一请求流上对比不同候选长度与接受阈值组合下的接受率、回退次数与延迟预算达成率，输出可比较的策略结论，并指出参数改变时哪些请求的判定结果发生翻转；策略对比须可由独立参考过程逐轮复算。
8. 支持把已处理请求的接受判定、回退记录与统计结果通过 sqlite3 持久化到本地库，进程中断后从最近提交点继续处理剩余请求，续算的逐请求结果与不中断全量处理一致；未提交的中间轮次不得写入已提交记录。

验收：
以独立参考投机解码器逐轮重算的接受判定、回退结果与统计为基准比对一致，且中断续算与两次重放结果完全相同。
