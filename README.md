当前是空白工作区，需要从零构建一个面向本地 Windows 环境的配置中心热更新中间件，作为数据处理管线与结果验证工具。用户在本地 JSON 文件中声明一组配置项（键、整数或浮点数值、需要参与计算的权重与聚合口径）以及订阅这些配置的本地计算任务；配置中心以版本号管理配置的每次变更，把变更推送给已注册的订阅者，计算任务按当前生效配置对确定性本地样本数据执行聚合计算并输出结果摘要。核心业务是：在热更新频繁发生的情况下，既要保证推送与查询的交互延迟可观测且受控，又要保证每个计算任务的结果与其所引用的配置版本严格对应，不允许出现新旧配置混合参与同一次计算。系统须支持把一次完整热更新会话（配置版本链、订阅关系、推送确认、各任务结果与版本标注）持久化为快照，重开快照后须能识别版本差异并整体替换状态。

任务环境与准备：
安装 Python 3.10 及以上版本，并确保 python 与 pip 在 PATH 中可用。
安装 NumPy 与 Tkinter（Tkinter 随官方 Windows 安装包提供，可用 python -m tkinter 检查可用性）。
创建空白工作目录，准备本地确定性配置样本、任务定义与聚合样本数据文件，全程不访问外部网络与真实服务。

业务要求：
1. 实现配置项与计算任务的加载及强校验：从本地 JSON 文件读取配置项定义与任务定义，配置项含键名、数值、类型与权重，任务含标识、引用的配置键集合与聚合口径；校验键名唯一且合法、引用的配置键必须存在、权重为受支持数值、聚合口径属于受支持集合，任一不合法须以 E_CONFIG 业务码整体拒绝加载并输出具体位置。
2. 实现配置中心的版本链与原子提交：每次配置变更生成新的单调递增版本号，版本记录包含变更键集合、完整生效值集合与父版本号；提交须经历暂存与生效两个阶段，任何时刻对某版本的读取只能看到该版本完整生效值集合，禁止读到部分键为旧值部分键为新值的混合状态；提交失败须以 E_COMMIT 报告并保留原版本不变。
3. 实现订阅注册与热更新推送：计算任务以配置键集合与期望版本声明订阅，配置生效后按订阅关系推送变更通知；推送须携带版本号与变更键集合，同一任务在收到推送后须能以一次原子操作取到该版本的完整生效值集合；推送失败须记录 E_PUSH 并可重试，重试不得让任务观察到中间版本。
4. 实现推送与查询的交互延迟观测：对每次推送与查询记录单调时钟起始与结束毫秒差，延迟样本按任务与版本聚合为均值、P95 与最大值，以整数定点表示并给出量化误差上界；观测须声明时钟基准与真值来源为本地单调计数，样本不足时输出 E_SAMPLE 而非以缺失值参与统计。
5. 实现计算任务结果与配置版本严格对应：每个任务按其引用的配置键从指定版本取生效值并对确定性样本数据执行聚合，结果摘要须记录所用配置版本、参与计算的键与数值口径；若任务引用的版本与其订阅版本声明不一致，须以 E_VERSION 拒绝产出结果，且不允许用当前最新版本静默替代。
6. 实现热更新并发下的结果一致性校验：多个任务在配置连续提交期间并发计算时，须保证每个结果只引用单一完整版本；提供校验命令，按结果摘要中的版本号重新取该版本生效值重算摘要并逐任务比较，不一致须以 E_VERIFY 报告并列出首个偏差任务、期望版本与实际版本。
7. 实现会话快照的版本识别与整体替换恢复：快照持久化配置版本链摘要、当前生效版本、订阅关系、推送确认记录、任务结果摘要与延迟统计口径版本；重开快照时须比较快照中的版本链摘要与当前会话是否一致，不一致须整体替换配置、订阅与结果状态而非增量合并，恢复后须能继续接受新版本提交。
8. 实现恢复后的重放校验与异常注入：从快照恢复后按快照记录的版本链重新推算每次提交的生效值与推送集合，并将任务结果摘要与延迟统计逐项比较，不可复现时以 E_REPLAY 报明具体依据；另支持以命令行参数注入配置文件损坏、订阅引用缺失、推送确认超时三类异常，分别以 E_CONFIG、E_SUB、E_PUSH 业务码报告并写入结构化日志，注入仅改变输入文件或参数。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
用本地样本验证热更新期间的推送延迟观测、结果与配置版本严格对应，以及快照版本识别与重放校验的一致性。
