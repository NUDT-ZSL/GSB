需求评审通过后，团队进入首次实现阶段，当前工作目录没有任何代码或样本，需要在 Linux（WSL Ubuntu）本地独立交付一个数据库主从复制延迟诊断与归档保留水位裁决引擎。全部输入由随工程交付的固定种子脚本确定性生成，不依赖真实数据库、外部服务或网络。业务对象包括：主库位点流（事务号、提交逻辑时钟毫秒、事务字节量、所属日志段号）、从库回放位点流（事务号、回放实例标识、回放逻辑时钟毫秒、回放结果、是否作废墓碑），以及两代保留策略描述：v1 为单文件 JSON，记录相对保留秒数、扁平回放实例映射与策略阈值；v2 为分片 JSON 加 SQLite 元数据库，记录绝对保留毫秒时刻、保留代数、依赖的检查点水位与失效墓碑。系统需在可注入逻辑时钟下合并位点流，计算每个从库的复制延迟，并裁决哪些日志段可安全归档、哪些必须保留供从库追赶，输出延迟诊断与归档裁决。

任务环境与准备：
在 Linux（WSL Ubuntu）环境安装 Python 3.10 或 3.11。
安装标准库 sqlite3 和 json，无需第三方依赖；如需定点计算可使用 decimal。
创建空工作区目录，并从工程交付目录复制固定种子脚本生成样本文件（样本为本地 JSON 与分片文件）。
确保样本输出写入合法目录，SQLite 元数据库可正常读写。

业务要求：
1. 解析并校验主库位点流、从库回放位点流与两代保留策略描述，确保事务号在主库和从库流内严格递增，日志段号连续且覆盖全部已提交事务，回放实例标识唯一，相对保留秒数为非负整数，绝对毫秒戳为整数，依赖的检查点水位存在且不回退，任何字段缺失或类型不匹配必须返回特定业务错误码，例如 E_BAD_STREAM。
2. 跨版本合并两代保留策略，同一回放实例在 v1 与 v2 中同时存在时依据策略声明的逻辑时钟与保留代数裁决最新版本，逻辑时钟相同则按来源格式优先级裁决；合并后每个策略节点保留来源版本、原始时间表示和裁决依据，v1 相对保留秒数在注入逻辑时钟下换算为绝对截止时刻并记录换算标度与舍入方向。
3. 在可注入逻辑时钟下计算每个从库的复制延迟，延迟由主库提交逻辑时钟与从库回放逻辑时钟之差转换得到，所有时间换算必须登记定点标度、舍入方向与被舍弃余量，未满一个定点单位的余量逐实例保留并参与后续累加，同一逻辑时钟序列下重复运行得到逐位一致的延迟值。
4. 计算每个保留策略节点所需的最小追赶余量和保留截止时刻，余量由未回放事务字节量按声明定点标度换算为逻辑时长，并累计加法与乘法误差上界；当两个日志段的保留截止时刻差小于容忍度且归档裁决依赖该差值时标记为精度敏感，输出参与比较的实例、误差来源链和若提高标度是否翻转裁决。
5. 裁决每个日志段的归档状态，取所有引用该段且未作废回放实例的保留截止时刻最小值作为最保守水位，结合注入逻辑时钟判定段为可归档、需保留或需告警；策略之间出现矛盾保留需求时输出冲突依据并映射到对应业务错误码，例如 E_CONFLICT_POLICY。
6. 支持保留策略更新和整体替换，策略以补丁形式提交时沿依赖边计算受影响的日志段和裁决结论闭包，精确标记哪些段需重估、哪些可安全复用；完整策略快照替换必须比较版本号、策略代数、签名集合和内容摘要，版本回退被拒绝，未受影响段的已提交裁决保持有效。
7. 实现持久化与强制终止后的恢复，把已提交位点流水位、回放实例的保留截止时刻、段裁决结论、精度敏感记录与逻辑时钟水位以事务原子写入 SQLite，进程在合并、延迟计算或裁决提交中途被强制终止后，恢复路径依据持久化状态识别已提交与半提交记录，只重放缺失部分且不重复计入。
8. 支持多进程并发一致性与幂等提交，允许多个裁决实例并行处理不同日志段或回放实例，通过 SQLite 事务与文件锁保证同一段同一策略版本只被裁决一次，同一策略快照只被整体替换一次，重复提交相同段结果必须幂等；提供命令行接口 load、merge、judge、resume、status、verify，status 以稳定排序 JSON 输出段状态与延迟证据。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。
