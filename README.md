当前是空白工作区，需要从零构建一个面向 Windows 本地环境的配置分发账本组件，用于教学与排障演示。系统管理若干逻辑组件节点的配置版本演进：用户以本地 JSON 清单声明一组配置项、节点目标与依赖关系（某配置项引用其他配置项，或某节点的分片依赖另一节点的派生结果），系统把每次版本演进编译为分发计划并记录成本账本（下发条目数、编译工作量与占用存储量以整数估算）。核心业务是：每次增量更新后仅重新编译受影响的条目，沿依赖图准确推导失效集合，并按容量与成本的显式权衡决定重编译、复用缓存还是丢弃缓存；同时把一次分发会话（清单版本、依赖图、产物版本、缓存占用与账本）持久化到本地 SQLite，会话在强制终止后须能依据持久化状态恢复，恢复时要识别版本差异并整体替换状态。

任务环境与准备：
安装 Go 1.21 或更高版本并确认 go 命令在 Windows 命令行可用，安装说明以官方文档为准。
使用 Go 标准库实现，SQLite 采用纯 Go 驱动，模块初始化与依赖下载在本地完成，不引入其他外部依赖。
准备本地确定性样本：若干版本配置清单 JSON、依赖成环样本、损坏清单样本与容量上限为零的参数样本。
准备演示脚本入口与本地运行说明，所有命令在 Windows 命令行下可直接执行。

业务要求：
1. 实现配置清单与依赖拓扑的加载与强校验：从本地 JSON 读取配置项、节点目标与引用依赖，校验键名唯一且合法、目标节点存在、依赖引用有效且拓扑无环；非法输入须以 E_SPEC 业务码整体拒绝加载并输出出错条目标识与原因。
2. 实现清单版本的增量更新账本：每次提交新版本仅对键值、引用或目标节点集合发生变化的条目生成新编译产物并递增产物版本，未变化条目的产物版本必须保持不变且可校验；版本变化后当前视图须整体替换而非增量合并，替换须在账本中记录版本差异。
3. 实现依赖失效传播与失效集合推导：当条目被修改、删除或产物版本变化时，沿依赖图推导全部直接与间接下游条目并标记其编译产物失效；删除仍被其他条目引用的条目须拒绝并返回 E_REF 列出引用者，传播顺序与失效集合须在多次运行中一致可复现。
4. 实现分发计划的容量成本估算：以整数单位估算每条计划的下发条目数与编译工作量，并按可配置的整数存储单价与编译单价合成总成本；估算须输出中间项且与输入规模相容，相同输入多次估算须得到同一整数结果，成本来源与接口版本须写入账本。
5. 实现容量与成本权衡策略：在缓存总容量上限约束下对每条受影响条目决定重编译、复用未被失效的缓存产物或丢弃缓存条目，须按确定性规则做取舍并输出决策理由与放弃复用的原因，不得依赖字典或哈希遍历顺序。
6. 实现失效传播后的账本一致性校验：提供校验命令，逐节点比较其应得配置组合与已下发产物集合，并校验失效集合、复用集合与最终账本成本是否自洽；不一致须以 E_LEDGER 报告并稳定列出首个偏差条目及其所属节点。
7. 实现版本识别的快照整体替换与恢复：快照持久化到本地 SQLite，含清单版本、依赖图版本、各条目产物版本、缓存占用与账本；重新打开快照时须比较快照清单版本与当前会话版本差异，不一致须整体替换依赖图、缓存与账本而非增量合并，恢复报告须列出版本差异与受影响的条目。
8. 实现恢复后的一致性重放校验与异常注入：从快照恢复后按快照记录的清单版本重新推导失效集合与分发计划，并与快照保存结果逐项比较，不可复现须以 E_REPLAY 报明具体依据；另支持以启动参数注入依赖成环、清单损坏、容量上限为零三类异常，分别以 E_DEPEND、E_SPEC、E_CAPACITY 报告并写入结构化日志。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。
