从无到有搭建时，需要交付一个面向 SQL 解析与逻辑计划领域的编辑与操作应用：用户以本地 JSON 描述一组视图定义（视图名、SQL 文本、依赖上游视图、逻辑时钟毫秒与内容摘要），并可对视图集合做新增、修改、删除三类编辑补丁；每次编辑后系统须把 SQL 解析为逻辑计划，沿视图依赖图计算受影响闭包，精确判定哪些已缓存的逻辑计划、列引用解析结果与可执行 SQL 需要失效重算，并给出可追溯的失效来源。样本还提供两代逻辑计划快照（v1 为单文件 JSON 的扁平列映射与相对生成秒数，v2 为分片 JSON 加 SQLite 元数据的绝对生成毫秒戳、计划代数与失效墓碑），核心难点在增量更新的依赖失效闭包与两代快照的互操作判定之间相互约束。

任务环境与准备：
Windows 本地环境，安装 Python 3.11 或 3.12（python --version 确认）。
执行 pip install sqlglot==25.24.5 安装 SQL 解析库；SQLite 使用 Python 标准库 sqlite3，无需额外安装。
在工作区根目录准备本地样本目录：views.json（视图定义集合）、snapshots/v1.json 与 snapshots/v2/ 分片加 v2_meta.db（两代逻辑计划快照），以及 patches/ 下的编辑补丁文件，内容自拟且格式自洽。
确认工作区可写，预留 SQLite 数据库文件与日志目录路径；不依赖网络服务、真实数据库或任何外部账号。

业务要求：
1. 实现视图定义集合与两代逻辑计划快照的解析校验：视图名唯一、SQL 文本可被解析器解析、依赖上游视图存在且依赖图无自环、逻辑时钟毫秒为非负整数、v1 扁平列映射条目均可追溯到已声明视图与列、v2 分片文件哈希与计划代数单调；非法输入必须返回明确业务错误码（如 E_BAD_VIEW、E_CYCLE）且不写入任何持久化状态。
2. 实现 SQL 文本到逻辑计划的确定性转换：用解析器把每个视图的查询转为含扫描、过滤、投影、聚合与联接节点的计划树，并抽取每个节点的输出列、谓词引用列与联接键；同一 SQL 在任意运行次数下必须得到逐字段一致的规范化计划与计划摘要，计划摘要作为后续依赖比对与失效判定的唯一基准。
3. 实现跨版本快照合并与统一计划视图构建：同一视图在两代快照中同时存在时，依据快照声明的逻辑时钟与计划代数裁决最新计划，逻辑时钟相同则按来源格式优先级裁决；合并后每个视图须保留来源版本、原始时间表示、裁决依据与被否决条目，且 v1 相对生成秒数在注入逻辑时钟下换算为绝对生成时刻时记录换算标度与舍入方向。
4. 实现编辑补丁驱动的依赖失效闭包裁决：以补丁提交视图新增、修改与删除，沿“视图—上游视图—列引用—已缓存计划—下游可执行 SQL”的依赖关系计算受影响闭包，精确标记哪些计划与下游视图需重算、哪些可安全复用；未受影响视图的缓存计划须逐字段保持不变，失效清单须输出触发来源与传播路径。
5. 实现列级依赖的细化失效与命名变化裁决：视图中投影列名变化、别名变化或删除被下游引用的列时，失效必须细化到引用该列的节点与视图而非整条查询；下游视图在解析期即可判定为不可编译时须返回独立业务错误码并输出被删除或改名的列名与引用位置，不得以运行期空结果冒充成功。
6. 实现编辑轮次的增量推进与整体替换：把当前计划快照指针、各视图计划摘要、失效事件与逻辑时钟水位以事务原子写入 SQLite，每次编辑产生新计划快照代数并以临时表加代数整体替换指针而非逐条覆盖；收到新快照包时比较代数、内容摘要与视图集合，判定完整替换、增量追加或无需操作，版本回退必须被拒绝并返回对应业务错误码。
7. 实现强制终止后的恢复与多进程并发幂等：进程在解析、失效计算或快照替换中途被强制终止后，恢复路径依据持久化状态识别已提交编辑与半提交计划，只重放未完成部分且不得重复计入失效事件或使视图计划出现新旧混合；多个编辑与查询实例并行时通过事务与文件锁保证同一视图同一计划代数只提交一次，重复提交相同补丁幂等。
8. 实现异常链路隔离与可重复命令行验证：SQL 语法错误、依赖成环、引用不存在的列、分片哈希不匹配、计划代数回退分别映射到不同业务错误码并在输出中保留可诊断字段（视图名、节点标识、编辑轮次）；单个视图编辑异常不得回滚其他视图的已提交计划；提供 load、edit、plan、resume、status、verify 子命令，status 以稳定排序 JSON 输出当前计划代数、各视图计划摘要与待失效事件数。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。
