架构评审已经收官，本地目录里除了需求说明没有一行代码和样本，团队要在此新工作区交付一个可运行的多租户分级缓存账本裁决引擎。系统围绕固定种子脚本确定性生成的存储缓存场景工作：租户配置给出租户名、最大缓存块数、软硬配额比例与逐出优先级权重；缓存条目流逐条给出条目序号、缓存键、租户名、L1/L2/L3 层级、块大小、访问逻辑时钟毫秒、访问计数和内容摘要；容量配置记录各层块数上限、总字节预算、重平衡阈值与冷却窗口逻辑毫秒。另外并存两代缓存策略快照，v1 是单文件 JSON，含相对生效秒数与扁平键到层映射，v2 是分片 JSON 加 SQLite 元数据库，含绝对生效毫秒、策略代数、条目墓碑和失效标记。引擎必须在可注入逻辑时钟下处理缓存准入、层级升降、逐出与容量重平衡，并同时保证两代策略合并增量失效闭包与中断恢复的账本一致性。

任务环境与准备：
在 WSL Ubuntu 中创建新工作目录，安装 Python 3.10 及以上和 SQLite 3 标准库。
随题交付一个固定种子样本生成脚本，执行后生成租户配置 JSON、缓存条目流 JSONL、容量配置 JSON 与两代策略快照文件到本地目录。
提供 requirements.txt 列出直接依赖（Python 标准库即可），确保所有命令在本地无网络环境下可执行。

业务要求：
1. 实现租户配置、缓存条目流、容量配置与两代策略快照的解析校验：租户名唯一且最大缓存块数与配额比例为合法正数，软配额不超过硬配额，条目序号严格递增且内容摘要与块大小一致，层级枚举合法，冷却窗口与重平衡阈值为非负整数，v1 相对生效秒数为非负整数且扁平映射均能追溯到已声明缓存键，v2 分片哈希与策略代数单调。
2. 跨版本合并两代策略快照并构建统一层级视图：同一缓存策略键在 v1 与 v2 同时存在时依据声明的逻辑时钟与策略代数裁决最新版本，逻辑时钟相同按来源格式优先级裁决；v1 相对秒数在注入逻辑时钟下换算为绝对毫秒并记录换算标度与舍入方向，未满一个定点单位的余量逐策略保留并在后续比较中参与，合并后每个条目保留来源版本、原始时间表示与裁决依据。
3. 基于两代策略合并结果计算增量失效闭包：当 v2 策略快照引入条目墓碑、失效标记或代数回退时，沿“策略键—缓存条目—租户配额—当前层级归属”的引用关系精确标记哪些条目层级、逐出决策和容量账本需要重估，哪些可安全复用；未受影响的条目状态不得被重算，失效闭包计算结果必须与对同一策略输入做全局重算的结果一致。
4. 在可注入逻辑时钟下执行缓存准入与层级升降裁决：按租户配额、各层总容量与热度得分（由最后访问逻辑时钟与访问计数固定顺序计算）判定条目是否准入以及目标层级，同一输入重复运行必须逐位一致；逻辑时钟回拨超过容差返回独立业务错误码且不改变已提交状态，所有时间比较只依赖注入逻辑时钟毫秒值，不读取系统墙钟。
5. 实现容量自适应重平衡调度：当某层占用超过重平衡阈值或总字节预算逼近上限时，按冷却窗口与重平衡阈值在层级间迁移条目，迁移必须满足目标层容量与逐出优先级权重双重约束，并在每轮逻辑时间预算内调度；预算耗尽时放弃剩余待迁移条目并记录放弃原因、受影响租户与被否决候选，严格区分预算内未启动、启动后失败与主动放弃。
6. 为层级升降、逐出与重平衡决策维护可校验的容量账本：每次状态变更在事务内更新条目层级、租户已用容量、各层占用摘要与策略版本指针，并以唯一决策序号登记；对同一输入集合执行全局一次性重算结果与增量推进结果逐条目逐字段一致，不一致时输出首个分歧决策序号、涉及条目与差异字段，容量账本任意时刻不得出现负值或超出声明上限。
7. 实现强制终止后的恢复一致性：把已提交决策序号、各条目层级与代数、租户已用容量、各层占用摘要、策略版本指针与逻辑时钟水位以事务原子写入 SQLite；进程在准入、迁移、逐出或策略合并中途被强制终止后，恢复路径依据持久化状态识别已提交决策与半提交决策，只重放未完成部分，不得重复更新账本、丢失墓碑或使容量读数超出上限。
8. 提供可重复命令行接口与多进程并发隔离：支持 load、merge、admit、rebalance、evict、resume、status、verify 子命令，多进程并行处理不同租户时通过 SQLite 事务与文件锁保证同一决策序号只提交一次、同一策略版本只被整体替换一次、容量账本不被并发超扣；status 以稳定排序 JSON 输出各租户已用容量、各层占用摘要与策略版本指针。
