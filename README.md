当前是空白工作区，需要从零实现一个本地数据库模式迁移与兼容诊断工作台（Windows 可运行，不依赖真实数据库服务）。本地样本以 JSON 描述一个业务库的多版本模式：v1..vN 每版含表、列、类型、非空与默认值、索引、视图与触发器，以及表间外键与视图/触发器对列、索引的引用关系；另有若干待执行的迁移脚本（以受控操作序列表达：加列、改类型、去列、建/删索引、改视图、改触发器），以及查询模板集合。工作台需要把多版本模式物化到本地 SQLite 样本库，按版本演进执行增量迁移，并在每次迁移后精确判定哪些查询模板、视图、触发器与索引的依赖失效、哪些可安全复用，最终输出可追溯的诊断报告。核心矛盾在于：增量迁移的原子提交、依赖闭包的精确失效、迁移中断后的恢复裁决三者相互耦合，任何一环处理不当都会让诊断报告与库的真实状态不一致。

任务环境与准备：
安装 Python 3.11 及以上版本，并创建独立虚拟环境（Windows 路径示例：python -m venv .venv 与 .venv\Scripts\activate）。
安装依赖：pip install numpy 以及标准库自带的 sqlite3（SQLite 版本需支持事务与临时表，可由 python -c "import sqlite3;print(sqlite3.sqlite_version)" 查看）。
在工作区创建 samples 目录，准备多版本模式 JSON、迁移脚本 JSON 与查询模板 JSON 作为本地确定性样本，准备一段演示脚本用于两次运行比对。
确认无网络访问需求，所有执行均在本地回环与本地文件系统完成；运行命令统一通过 python -m 入口执行。

业务要求：
1. 实现多版本模式样本与迁移脚本的解析校验：表名、列名、索引名、视图名与触发器名在各自作用域内唯一，类型枚举合法，默认值类型与列类型相容，外键两端表列存在且类型可比，迁移操作引用的对象与顺序合法；非法样本或脚本必须返回明确的 E_xxx 业务错误码并保持库与元数据完全不变。
2. 实现迁移的增量执行与依赖失效闭包判定：以补丁形式执行迁移操作后，沿“列—索引—视图—触发器—查询模板”的引用关系计算受影响闭包，精确标记哪些查询模板改写缓存、视图定义、触发器绑定与索引可用性必须失效重建，哪些可安全复用；未受影响模板在迁移前后必须给出完全相同的结果，失效清单须可追溯至触发操作。
3. 实现迁移原子提交与版本指针整体替换：每次迁移产生新版本号并以内容摘要标识，提交时以临时表加版本号整体替换当前模式指针而非逐条覆盖；收到新版本时比较版本号、操作摘要与对象集合，识别完整替换、增量追加与版本回退，版本回退必须被拒绝或按策略降级并在诊断报告中标注。
4. 实现迁移过程中的强制终止恢复裁决：把迁移阶段、已提交操作、模式版本指针、对象摘要与未完成事务登记以事务原子写入 SQLite；进程在加列、改类型或重建视图任一阶段被强制终止后，恢复路径依据持久化状态识别已提交操作与半提交操作，只回放未完成部分，不得重复执行已提交操作或让库停留在半迁移状态。
5. 实现查询模板在迁移后的改写裁决与结果一致性校验：按当前模式版本改写模板中的列引用、表引用与类型相关表达式，改写结果须与在原始模式版本上执行得到的结果在语义等价时逐行一致；当改类型导致精度或取值范围变化时，必须区分不可兼容改写与精度损失改写，并输出首个受影响列的原始类型与新类型。
6. 实现迁移轮次的可复现观测与精度记录：所有迁移执行顺序、默认值换算与类型转换的中间值须记录运算顺序与定点标度（如数值类型缩放），相同输入重复运行必须得到逐位一致的迁移结果与诊断报告；当类型转换的截断或舍入使两条查询模板的判定结论差小于给定容差时标记为精度敏感并输出误差来源链。
7. 实现多进程并发一致性与幂等提交：允许多个迁移实例与诊断读取实例并行，通过 SQLite 事务与文件锁保证同一模式版本只提交一次、同一迁移操作重复提交幂等，读取方只能看到完整已提交的模式版本而非迁移中间态；并发冲突须返回可诊断的错误码而非静默覆盖。
8. 提供模式诊断命令行与可重复演示：支持 load、migrate、explain、resume、status、verify 子命令；explain 以稳定排序 JSON 输出指定模板的失效原因、改写后语句与依赖路径，status 输出当前模式版本、各对象版本与失效计数，verify 校验持久化元数据与 SQLite 实际模式一致，演示脚本两次运行输出完全一致。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。
