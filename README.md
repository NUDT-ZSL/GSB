制品仓库的元数据服务保存着海量构建任务记录，依赖分析作业需要按触发时间戳升序消费这些记录以还原依赖链。记录量经常超过进程可用内存限额，必须走外部排序：先分块排序溢写磁盘，再多路归并成全局有序流。困难来自输入本身——同一毫秒常有大量并发触发的构建任务，时间戳在批次间存在回拨，制品键含 UTF-8 混合字符，任务状态字段取值稀疏且有大量重复。运维要求每次排序都能复算：既要输出全局有序结果，也要给出溢写段数、归并趟数、峰值内存与临时文件总大小的运行账目。数据库中已有一张构建任务元数据表作为原始数据来源，内核需从该表读取记录并回写排序结果。

任务环境与准备：
准备 Linux（WSL Ubuntu）上的 Python 3 运行环境，仅使用标准库中的 sqlite3、heapq、json、argparse、tempfile 等模块，无需安装第三方包。
在空工作区中创建项目目录，运行前由题内确定性生成器按固定种子在本地 SQLite 文件里建立 build_task 表并填充构建任务记录样本，样本包含重复时间戳与回拨段。
通过命令行参数声明内存限额、归并路数上限与工作目录，在本地执行分块溢写与多路归并以产生结果表与运行账目 JSON。

业务要求：
1. 实现分块溢写阶段：从 SQLite 的 build_task 表中按主键顺序流式读取记录，按 --mem-limit-bytes 声明的内存限额切块，对每块在内存中按（trigger_ts 升序，输入序号升序）稳定排序后写入编号连续的临时段文件，段文件内记录以长度前缀加内容编码，保证读取端可精确解析段边界。
2. 为每个段文件维护清单条目，记录段编号、记录数、字节大小与首末记录的时间戳，并将清单以 JSON 形式持久化到工作目录，使归并阶段可脱离溢写阶段的进程状态独立启动并校验清单完整性。
3. 实现多路归并：以 heapq 维护各段当前读取位置的最小堆，按（trigger_ts，输入序号）比较输出，每次仅持有一条记录与各段读取缓冲，逐条写出结果表，并在每段读取完毕后记录其消费位置偏移，支持中途停止后从清单恢复续读。
4. 归并路数受 --max-fan-in 限制；当段数超过路数上限时执行多趟归并，每趟将相邻若干段合并为中间段并更新清单，直至剩余段数不超过上限，最终趟输出为全局有序结果；每趟结束需回收被合并段的磁盘空间。
5. 在输入时间戳发生回拨与重复时仍保证稳定：相同 trigger_ts 的记录输出顺序必须与输入序号顺序一致，且重复时间戳块被拆分到不同段时其相对顺序不得因归并趟数变化而改变。
6. 统计并输出外部排序运行账目 JSON，包含溢写段数、每段记录数、归并趟数、峰值内存使用量（按块内记录字节与堆缓冲实时度量）与磁盘临时文件总大小，供依赖分析作业作为可复算依据存档。
7. 保证峰值内存不超过 --mem-limit-bytes：块切分需按记录实际序列化字节累加而非按条数估算，遇到单条记录本身超过限额时须以明确业务错误码拒绝并清理已写临时文件，不得静默截断。
8. 归并过程中按需删除已完全消费的临时段文件，正常结束或被业务错误中断时均须清理全部临时文件；通过账目中的临时文件总大小与工作目录剩余文件清单验证无磁盘泄漏。

验收：
以题内确定性生成器构造的内存稳定排序参考序列逐条核对输出顺序与内容，并检查重复时间戳稳定性、账目字段与临时文件清理情况。
