# 设计与不变量

## 进程模型

中间件是一个 Go 进程，所有格式转换、语义判定、偏移分配和日志追加由 `Engine.mu` 串行化。网络 I/O 和 JSON 编解码可并发，但会影响持久状态的临界区只有一个，因此并发发布不会出现两边同时成功写入相同幂等键的窗口。

每个消费者在一个连接上只有一个写循环，保证发给该消费者的消息顺序稳定。不同消费者可并行收消息；底层追加日志仍由统一锁串行写入。

## 发布路径

1. 按行读取 JSON，识别请求类型。
2. 严格校验字段集合、字段类型、版本和语义能力。
3. 恰好一次消息在引擎锁内查询 `idempotency_seq`。
4. 新消息先追加并 `fsync` `messages.log`，再追加 `dedup.index`。
5. 更新内存索引，唤醒消费者会话。
6. 返回接受结果或既有结果。

若第 4 步之后进程崩溃，恢复会从消息日志重建去重索引；若消息日志没有完整帧，则该消息不会被恢复。消息日志是消息接受结果的最终依据。

## 版本转换

源消息字段集合完全由源版本决定，不依据零值猜测。目标字段先按声明版本构造，再计算：

- `stripped_fields = source_fields - target_fields`
- `filled_fields = target_fields - source_fields`
- 重试计数按语义重新计算
- 每个目标字段记录来源类型

语义键在内部 `StoredMessage` 上独立保存，不因载荷降级而丢失。因此 v3 恰好一次消息可以安全投递给 v1/v2 订阅者，中间件仍以原始幂等序列完成全局去重。

## 消费者状态

每个消费者保存：

- `NextOffset`：下一个首次投递可用的本地偏移；
- `AckedOffset`：当前最大已确认偏移；
- 每个全局消息的投递状态：本地偏移、attempt、最后 session、是否完成、是否确认。

同一消息重投时沿用首次分配的本地偏移；首次投递新消息时偏移单调加一。这样确认偏移和实际投递一一对应。

至多一次在调度时标记完成。至少一次和恰好一次在收到确认后才完成。恢复时所有旧 session 标记被清空，因此未确认的至少一次消息无需等待重试定时器即可在新进程的首个订阅中重投。

## 日志帧

```text
{"seq":<单调序号>,"crc32":"<8 hex>","record":<记录>}\n
```

- 写入在统一锁内完成，每条记录调用一次 `Write`，随后 `Sync`。
- `crc32` 对序列化后的 `record` 计算。
- 追加快照由临时文件、`Sync`、原子 `Rename` 完成。
- `consumer-offsets.json` 仅用于观察和快速读取，真实状态始终可从 `deliveries.log` 与 `acks.log` 重建。

## 恢复流程

1. 逐个扫描四个日志/索引文件。
2. 校验 JSON、序号和 CRC32。
3. 仅允许截断文件末尾不完整或 CRC 错误的帧；中间损坏直接拒绝启动。
4. 从 `messages.log` 重建消息列表和 `idempotency_seq -> message` 去重映射。
5. 从 `deliveries.log` 重建消费者偏移、attempt 和完成状态。
6. 从 `acks.log` 标记确认并更新最大已确认偏移。
7. 对比 `dedup.index` 与消息映射，补齐缺失条目。
8. 原子写入新的偏移快照和 `recovery-report.json`。

恢复报告包含：

- 每个消费者已恢复偏移；
- 重建的消息、投递、确认和去重条目数量；
- 最后消息全局偏移；
- 尾部处理动作、截断字节数及每个问题帧的偏移/原因；
- 恢复后的消费者快照。

## 顺序保证

- 同一分区键的日志顺序等于引擎锁内追加顺序。
- 消费端遍历全局消息偏移，因此同一消费者看到的分区消息顺序等于日志顺序。
- 不同消费者可以交错接收，但各自流内顺序稳定。
- 单帧一次写入、长度和 CRC 校验共同避免半条记录被当作有效状态。

## 验证不变量

验证器按以下不变量检查最终状态：

1. 每条投递可回溯到源消息标识和源版本。
2. 转换方向与源/声明版本一致。
3. 载荷字段集合严格等于声明版本字段集合。
4. 剥离和补齐字段集合由版本差集唯一确定。
5. 补齐默认值、时间戳、分区键和幂等序列符合规则。
6. 至少一次重试的 attempt 连续，重试计数按 `源值 + attempt - 1` 递增。
7. 至多一次每个消费者至多出现一次。
8. 恰好一次消息和幂等索引一一对应，无重复。
9. 消费者偏移首次出现连续、单调；重投不得改变偏移。
10. 确认必须对应已投递偏移，确认后不得再出现该消息投递。

任一偏差生成 `E_VERIFY`，不会静默忽略。

## 边界

- 本实现面向本机确定性验证，使用全局单写锁换取简单明确的顺序与去重不变量。
- 所有历史消息保存在内存索引中；适用于演示和中小规模本地会话。
- 消费者标识是状态边界，服务不实现多租户、认证或网络加密。
- 新消费者默认从最早匹配消息开始；如需“仅新消息”策略，可扩展订阅起始偏移，但不属于当前验收范围。
